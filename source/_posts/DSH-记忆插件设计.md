上一篇《[Agent 的记忆怎么做：四份开源实现的拆解与取舍](/2026/11/11/Agent记忆/)》拆了四家方案的设计取舍。这篇把镜头收回来，对准**我机器上真装着的那一个**——一个跑在宿主进程内的分层记忆插件，版本 0.26.29。

封面那张图就是它的运行时数据流：左边是会话事件，中间是插件，右边是宿主核心，黄色是写入，蓝色是召回。图是项目自带的，我原样搬了过来（见文末「边界」里关于封面比例的一点说明）。

先给一句总括：

> **它不是一个"外挂钩子"，而是宿主进程里的一组事件缝；它也不是"把聊天记录存下来再检索"，而是一条后台异步运行的四层编译管线，加上一条每轮请求之前把编译结果注回去的前置缝。**

这篇全部结论来自装好的实现本体、项目自带文档与本机数据的实测，不是从 README 抄的。凡文档与代码说法不一致的地方，一律以代码为准，并且会把这处不一致点出来。

## 0. 先回答那个最容易误解的问题：它是 hooks 吗

**是钩子，但不是你可能想到的那种钩子。**

很多 Agent 框架里的"hooks"指的是一份外部配置：写 `hooks.json`，注册 `UserPromptSubmit`、`PreToolUse`、`PostToolUse` 之类的事件，由宿主在对应时机**拉起一个外部命令**，把 JSON 从 stdin 喂进去、读 stdout。宿主本身也确实支持这套桥接协议，还会把不认识的类型（http、mcp_tool、prompt、agent）跳过并告警。

这个插件一条都没用。它走的是**宿主进程内的事件总线**：插件作为 Cordis 座位被装载进同一个 Node 进程，直接订阅宿主派发的事件。四条缝是：

| 缝 | 事件 | 干什么 |
| --- | --- | --- |
| 捕获缝 | `session/event` | 按轮次缓冲 user/assistant 消息，遇 `turn/end` 结算一轮，把消息交给蒸馏管线；同时登记水位 |
| 注入缝 | `agent/pre-step`（waterfall 中间件） | 每轮新用户输入之前，把检索到的相关记忆**作为额外一条 user 消息**插到消息序列最前面 |
| 稳定区缝 | `systemPrompt.context({ name: 'memory:profile', order: 510 })` | 把画像、场景导航、工具使用指南放进系统提示词的固定段位 |
| 生命周期缝 | `agent/created` / `agent/disposed` | 压缩/清空后重置去重账本、清占用统计；`resume` 时补收崩溃期间漏掉的轮次 |

注入缝的实现有个值得一提的细节：它是**先 `await next()` 让其他监听器跑完，再改写结果**，而不是抢在前面劫持。所以别的段位该加的上下文照加，插件只在结果消息数组前面 prepend 一条；任何异常都只 warn 并原样返回，**绝不因为记忆出问题而拦住一轮对话**。

除了这四条缝，插件还做了三件不靠钩子的事：用 `ctx.tools.register` 注册了 **23 个** `memory_*` / `conversation_search` 工具（你能直接调用的那批）；用 `connection.rpc.handle` 开了一组 RPC 给设置页和侧栏卡片；以及把 L1 记录同步投射成 `.memory.md` 文件。

{% mermaid %}
flowchart LR
    U[用户一次输入] --> PS[agent/pre-step 中间件]
    PS -->|prepend 一条相关记忆| C[宿主核心组装请求]
    ST[systemPrompt.context 稳定区] -->|画像 + 场景导航 + 工具指南| C
    C --> M[模型作答]
    M --> SE[session/event 按轮次缓冲]
    SE -->|turn/end| R[后台蒸馏管线]
    R --> DB[(主表 / 场景文档 / 画像 / 账本)]
    DB -->|下一轮检索| PS
{% endmermaid %}

还有一个边界得先划清楚：这套插件**只做长期记忆那一半**。上下文窗口快满时的压缩、折叠、还原，由同一个 profile 里另一个独立的 bundle 承担（就是这轮对话里给我 `compress` / `decompress` 能力的那个）。两者互不Import、互不调用，只是恰好装在一起。所以别指望它解释"长对话怎么变短"，那不是它的活。

## 1. 四层不是四个库，是三次不同的 LLM 问答

"L0 到 L3"听起来像四级存储，实际是**同一条流水线上三次不同形状的模型调用**，工程侧照着输出写不同的东西。

先纠正两个常见想象：

- **L0 不是"原文一字不改的流水账"**。这个版本起，L0 正文已经**停写**——会话原文由宿主侧的会话收集器（DRSC）投影供给，插件只登记水位、不落原文；而且写入路径默认开脱敏，PEM 私钥、Bearer/JWT、Cookie、厂商 API key、邮箱、长号、高熵 ID 等 8 类会被替换成 `[REDACTED:<KIND>]`。想找原文，走 `conversation_search` 去查收集器，不是查这个插件。
- **L1 也不是轻飘飘的一张卡片**。它是带族、有效期、优先级、来源锚点、冲突标记、决策凭证的唯一写面真源，后面会反复回到这一点。

三次调用分别长这样：

| 层 | 动词 | 输入 | 输出 | 落到哪 |
| --- | --- | --- | --- | --- |
| L1 | **抽** | 本轮消息切片 + DRSC 拉来的会话尾窗做背景 | 且仅一个 JSON 数组，每项含场景名、消息 id、记忆数组 | SQLite 主表一行 + 一份 `.memory.md` |
| L2 | **并** | 本批新卡片 JSON + 本族**全部**场景摘要 + BM25 挑出的 3 个相关场景全文 | 且仅一个 `write`/`delete` 文件操作数组 | 场景目录下的 Markdown 文档 |
| L3 | **蒸** | 上次画像之后**有变化**的场景全文 + 旧画像 | 一整份 `persona.md` 文档 | 画像文件，整体覆盖 |

L1 的提示词要求记忆"跳出当前对话依然成立"，状态断言自带时点与范围，宁缺毋滥。真实抽出来的一条长这样（本机库里的一行）：

> 结论：用户的 GitHub 账号是 BenedictTom（显示名 chw），此前按 SSH key 注释推测的 caohongwei 是错误账号。依据：2026-10-30 用用户提供的 fine-grained PAT 调 GET /user，返回 login=BenedictTom、name=chw。适用范围：本机对该账号的所有 git/GitHub 操作都应使用 BenedictTom。

一句话里塞了**结论 + 依据 + 适用范围 + 时点**，这是抽取 prompt 刻意训练出来的形状，不是模型自由发挥。

L2 的产物是一份 SOP 手册的一章：META 块（创建/更新时间、摘要、热度）加 `## 工作场景` / `## 适用条件` / `## 核心 SOP` / `## 判断逻辑` / `## 禁忌与反模式`。L3 的产物是"这个用户/团队是谁"的画像文档——你在这轮对话开头看到的那两块 `<domain family="work">` 和 `<domain family="chat">`，就是这两份文件的原文，逐字注入。

**关键纠偏**：L2 不是"从 L1 抽取"。它是拿本轮新卡片去**增量整合已有的场景档案**：LLM 吐出 `write` 操作，content 必须是含完整 META 块和全部章节的整份文档（不是补丁），工程侧整体重写。L3 更彻底，完全不碰 L1，只读变化的场景 + 旧画像，输出整份文档整体替换。所以动词是**抽、并、蒸**，不是一路"抽"到底。

三次都攒批触发，各层阈值不同、按族各自计数：L1 攒够若干条消息、L2 累计 5 条新记忆、L3 累计 20 条。这也是为什么单次蒸馏是"真实 LLM 调用、实测 70 秒以上"，不能每轮都跑。整条链路连同两条旁路，画出来是这样：

{% mermaid %}
flowchart TD
    MSG[会话消息切片 + 会话尾窗背景] -->|攒够消息| L1[L1 抽：JSON 数组]
    L1 -->|原子事实卡片| DB[(主表 / 全文索引 / 向量 / 文件投射)]
    L1 -->|本族累计 5 条新记忆| L2[L2 并：write 与 delete 操作数组]
    L2 -->|整体重写| SC[场景文档 scenes 按族分目录]
    SC -->|累计 20 条 或 变化场景| L3[L3 蒸：整份画像文档]
    L3 -->|整体替换| PE[画像 persona 按族分文件]
    DB -.->|派生投影旁路| GR[图谱]
    DB -.->|同一批新记录旁路| SK[技能结晶]
    PE -.->|每轮前置注入| PS[agent/pre-step]
    SC -.->|场景导航| PS
    DB -.->|相关记忆检索| PS
{% endmermaid %}

注意图谱和技能结晶都不经过 L2：它们吃的是同一批 L1 新记录，不是场景文档。

## 2. 族与类型：先定共享面，再定标签

这是整套设计里最容易被读反的一对概念。

**族（family）只有两个：`chat` 和 `work`。** 注意别被配置里的 `auto / chat / work` 骗了：那是**会话档位**（决定这一轮往哪个族写、以及 `off` 档直接隐身不捕获），不是族本身。族是共享面的边界。

**类型（type）有 36 个可赋值项**：29 个宿主类型（`user_*` 四个、`project_*` 九个、`development_*` 四个、`*_experience` 十二个）加 7 个旧类型（`persona`、`episodic`、`instruction`、`work_fact`、`work_task`、`work_method`、`work_artifact`）。另有 1 个兜底目录名，它不是可赋值的类型，自成一类。

静态词表层，每个 type 都在一张表里登记到某个族：旧类型看 `work` 前缀，宿主类型看 `user_` 前缀，`work_fact` 归 work，`user_hobby` 归 chat，兜底归 chat。所以"type 归属于 family"这句话，在字典层面成立。

**但运行时的方向是反过来的：family 优先，type 兜底。** 抽取 prompt 里写得很直白——"先定族，再选型"，每条记忆必须显式输出 `family`，判定"只看语境，不看内容形状"，并且**族决定该族可选的 type 词表，不许交叉**：chat 族只能挑 chat 的类型，work 族只能挑 work 的。落库时由一条三级链定案：

> 会话档位强制 > LLM 显式输出的 family > 按 type 查字典回落

于是两者是**正交**的两根轴，各管各的：

| | family 决定 | type 决定 |
| --- | --- | --- |
| 场景文档放哪 | `scenes/<family>/` | — |
| 画像文件 | `persona-<family>.md` | — |
| L2/L3 攒批计数 | 每族独立 | — |
| 去重候选池 | 只在本族召回，永不跨族 | — |
| 文件投射目录 | — | `memories/<type>/` |
| 检索过滤 / 面板标签 | — | `memory_search(type=)`、中文标签 |

还有一个刻意的解耦：`applicability`（跨项目 / 单项目 / 单会话）由抽取 prompt 单独产出，**绝不从 family 推导**。"工作族的记忆"和"这条记忆能不能跨项目用"是两件事，硬绑一起会出事。

## 3. 场景与画像：怎么把便利贴编成手册

L2 这次调用喂进去三样东西，顺序和取舍都挺讲究：

1. **本批新卡片的 JSON**：只带 `record_id`、content、type、priority、场景名、适用性与时间戳。
2. **本族全部场景的摘要一览**：一行一个，格式是 `` `路径` | heat | updated | 摘要 ``，附"当前场景总数"。本机 work 族现在是 11 份场景文档，这 11 行全进 prompt。注意**是全部摘要，不是全部全文**——全文太贵。
3. **BM25 挑出的 3 个相关场景全文**：回读文件后塞进 prompt 的「相关场景完整内容」一节，并注明"仅供参考，write 时必须整体重写，不要只改局部"。

BM25 这一步容易被误读。它不是拿全文建索引：索引文档是「**摘要 + 文件名**」，query 是**本批新卡片 content 拼起来**，参数 K1=1.5 / B=0.75，分词用 jieba 词加 CJK 二元组并集（和主检索的 FTS 共用同一套分词器），按分数取 top 3，再回读这三份的全文。也就是说，它回答的是"这批新卡片最可能该归到哪几份场景里"，而不是"最像哪句话"。

输出侧是硬约束：LLM 明确被告知"**你无法直接操作文件**"，只能返回且仅返回一个 JSON 数组，每项 `{"op":"write","path":"场景文件名.md","content":"完整文件内容（含 META 块，≤1500 字符）"}` 或 `delete`；`content` 必须是完整文档不是局部补丁；禁止创建 REPORT/SUMMARY 这类一次性文件。工程侧逐条执行，单块失败只丢该块、不影响其他块。文档里还有个 `[PERSONA_UPDATE_REQUEST]` 标记，用来顺带请求刷新画像。

这是它与上游 MemoryCore 的一处明确差异：原版让 LLM 用"操作文件的工具"自己改，这里改成 **LLM 只输出操作 JSON / 完整文档，由工程侧执行**。同样的思路在 L3 更彻底——直接输出一整份 `persona.md` 正文，工程侧整体替换。好处是写面完全可控、可校验、可回滚；代价是每次都要重吐整份文档，字符预算卡得很死（L3 ≤ 2000 字符）。

L3 的增量的做法也和 L2 不同：它用一个 `lastL3At` 时间戳水位，只挑 `updated > 水位` 的场景全文，加上旧画像，判模式为首次还是增量。所以 L3 是**读侧水位**，L2 是**计数 + 本轮**——这个不对称，正是下一节那个缺口的根。

顺便说一句本机实况：chat 域的画像至今还是冷启动空白（`totalExtracted=0`），work 域那份已经写到 11 个来源场景、646 条记忆。双域完全隔离，一边的空白不会渗到另一边。

## 4. 图谱不是第五层：它是 L1 的派生投影

图谱在这套设计里的定位很克制：**不是独立的一层记忆，而是 L1 的确定性派生视图**。

项目把它写成一条不变量——"**零无源事实**"：每个节点、每条边都必须能沿 `sourceRecordIds` 点查回现存的 L1 记录。因此写面的唯一真源永远是 L1，**纠正 = 改源 + 重投，不是手写 SQL**；插件不提供、也不打算提供绕过投影直写图谱表的入口。

存储上是三张域表（节点、边、投影任务）加两张 job 索引表（记录→任务、记录→已投影凭证）。调度上有几条工程约束值得抄：

- **LLM 永不进事务**：`claim` 与 `complete` 是两个独立事务缝，模型调用在事务外。
- 按 **record_id 记账**：扫描"还没投影过"的记录时用 `NOT EXISTS` 查已投影凭证表，按创建时间排序入队；成功后才写凭证、删在途映射；失败按 attempts 分类、退避，attempts ≥ 3 的 job 不再被 claim。
- 凭证带 `projector_version`：投影器版本一变，旧凭证自动失效，重新投影。
- `disputed`（争议）是派生字段，随待裁决冲突队列重算，不单独存。

纠正通道有三个工具，语义都是"改源 + 重投"：修订一条记忆（读旧 → 造 version+1 的新 id → 旧行软删 → 新旧一起强制重投，旧源支撑的边标墓碑）、强制重投影（抹掉"已按当前版本投影"的凭证、按高优先级重入队，幂等）、迁移关系（先硬校验所有源记录现存未退场，再闭旧边出新边，并新增一条承载新关系的 L1 源记录）。

**默认关闭。** `graphEnabled` 默认 false，`graph.enabled` 部署配置也关着；没开的时候工具直接回一句"知识图谱未启用"。本机实测 `graph_nodes=0`、`graph_edges=0`。所以这篇里关于图谱的都是"设计"，不是"这台机器上正在跑的东西"。

## 5. 那个"只带本轮"的缺口，以及可以怎么补

这是我在读实现时卡最久、也最想写下来的一处。

L2 的触发条件是"**某族累计 ≥ 5 条新 L1**"。计数器每写一条 L1 就 +1，跑完 L2 归零。但真正送进 L2 的 `familyRecords`，是**本轮 `newRecords` 里筛出来的**，不是"历史上所有没整合过的记录"。

于是有个反直觉的推演：假设前 4 轮每轮各抽出 1 条卡片，计数器攒到 4；第 5 轮又抽 1 条，计数器到 5，触发 L2——但这一轮的 `newRecords` 里**只有第 5 轮那 1 条**，前 4 条不在里面。于是 5 条新记忆里只有 1 条真正进了场景整合，跑完计数归零，前 4 条失去了这次整合机会。

{% mermaid %}
flowchart LR
    A[第 1–4 轮 每轮抽 1 条] --> B[计数 1 → 2 → 3 → 4]
    A2[第 5 轮 再抽 1 条 计数到 5] --> C[触发 L2]
    B --> A2
    C --> D[familyRecords 只装本轮 1 条]
    D --> E[跑完计数归零]
    E --> F[前 4 条仍在主表 可被召回]
    E --> G[但没进这次场景整合]
    F -.-> H[反刍或重建的全量兜底才可能补上]
{% endmermaid %}

要先说清楚**丢了什么、没丢什么**：4 条卡片**没有丢**，它们好好躺在主表里，`memory_search` 照常能召回，工具也查得到。丢的是**它们对场景文档的归纳贡献、以及经由场景对画像的贡献**。而且计数一归零，反刍的轻量刷新、重建的收尾都因为 `newMemoriesSinceL2 <= 0` 认不出还有残留；只有手动触发的全量反刍会把记录整批（limit 500）重灌一遍。

**为什么这么设计？** 不是为了省事，是一次明确的事故修复。0.26.9 的「蒸馏分块分载」改动记录里写得很清楚：旧版"一次把整族 backlog 塞进单调用，库越大越必撞超时"（实测 work 族 L2 超过 60 秒被中止），于是改成 24k 字符硬顶分块、且只带本轮。重建模块里还有一句坦白话："正常轮次语义里差几条不触发是常态"——**正常轮次走增量，一致性交给反刍/重建的全量补**。加上单次 LLM 实测 70 秒以上、L2 又是整份文档覆盖写（重复整合代价高），攒批 + 只带本轮就成了成本上的合理取舍。

**但它不是架构上的必须。** 最能说明这点的是：同一个插件里的图谱投影，就是按 record_id 精确记账的——三张表、`NOT EXISTS` 扫未投影、成功后消账、失败重试，一个"哪几条没处理过"的账本现成摆在那儿。L2 没这么做，是那次修复只治了超时、没换账本。

真要换成 per-record 水位线，得顺带补四件事，否则只是把坑挪个位置：

1. **失败不消账**：成功整合后才标记，配 attempts/退避/dead，而不是"送进去就清零"。
2. **"送进去" ≠ "整合了"**：L2 是 LLM 输出 `write`/`delete` 后整体重写，不是确定性投影。一条记录被引用进某个场景，得有可验证的落点才算数。
3. **记录变更要失效**：修订、退场、恢复、改名都得让旧标记作废（图谱用的是 `projector_version` + 失效重投）。
4. **按族分开**：族是共享面，账本也得按族切。

我的判断是：**这不是做不到，是"正常轮次先跑起来、一致性交给后台兜底"的优先级选择**。它把最坏情况从"整族超时"换成了"少量记录晚一点进场景"，在长 LLM 调用这个成本结构下说得通；代价是计数归零把残留抹平了，兜底路径又依赖人去触发。

## 6. 遗忘：不是删掉，是退出检索面

这套系统对"遗忘"的态度，一句话概括是**可逆优先，物理删除是例外中的例外**。

### 一个原语，三条路径

人工删除、去重取代（`update`/`merge`）、冲突裁决判负——这三条看起来毫不相干的路径，**共用同一个退场原语**：在记录的元数据里写一个取代标记（含时间、原因、裁决结论、对手 id 等），保留主表行，只把该行从 FTS / 向量索引里撤掉；同时联动投射文件（改名加失效后缀或重建）和图谱（把该记录支撑的边标墓碑）。

几个细节能看出它被踩过坑：

- **判据单源**：只有取代标记说了算，坏标记（缺时间或缺原因）一律当**活动记忆**处理——"宁可把一条坏标记的记录当活动记录，也不把它当已退场而藏起来"。
- **一处文档漂移**：README 的表格仍写着退场会"闭合 `valid_to`"，但实现里明确写着"**只写 marker，不再闭合 `valid_to`**"。原因是旧口径把"过时 / 历史区间 / 软删"三件事塞进同一列，导致"2020 年结束的一次旅行"这类**合法历史**被静默遮蔽。现在 `valid_to` 回归纯粹的现实有效期。按代码为准，以"只写标记"理解。
- **默认只退场 1 条**：`memory_delete` 的上限被从 3 改到 1，注释里直说原因是"实测发生过一次真实误删"。给了 id 就走精确路径、不做语义匹配。
- **恢复**只剥标记、重建索引；"回到主表" ≠ "回到召回"，想一步回滚得显式加参数。
- **物理清理**是全插件**唯一不可逆**的动作：默认干跑，先落全库快照并按内容哈希校验，不一致即中止且一条不删；快照可列表、可恢复，恢复入口只收目录名不收路径。清理函数里还有一道门禁——只清"确实带退场标记"的行，注释说得很直白：否则任何调用方传一个 id 列表就能绕过软删、把活动记忆直接物理抹掉。

**修订也不是覆写**：`memory_update` 是读出旧记录 → 造一条 version+1 的新 id → 旧行带 `superseded` 标记退场。事实源是 append-only 的，旧版本随时能 restore。代价是频繁修订会累积版本行，规模由物理清理控制。

### 四根轴、六个状态

一条记忆的"时间性"被拆成**四根互不替代的轴**：退场方式（取代标记）、有效性定性（查询期派生的六态）、客观持续性（`t`/`o`/`s`/`p`）、现实有效期（`valid_to`）。查询期派生出六种状态：

| 状态 | 进索引 | 被动注入 | 工具查 |
| --- | --- | --- | --- |
| `current` / `historical` | ✅ | ✅ | ✅ |
| `expired`（有效期闭合且来源可信） | ✅ | 需开灰度闸才剔除 | `include_expired` 放行 |
| `expired_suspect`（来源不可信） | ✅ | ✅ 带"疑似失效"标注 | ✅ |
| `superseded` / `retired` | ❌ 已撤出 | ❌ | 仅取代链反查 |

这里我最喜欢的一条设计是：**默认检索只剔除"可信 expired"，`expired_suspect` 保留**——注释叫"疑而不隐"。来源不可信的过期判断不足以让一条记忆消失，最多带个标注。六态是查询期谓词、不落库，所以同一条记录在不同时间点查，状态会自然变化。

三扇门控制严格程度：门 1 是退场判据（含升版首启的 FTS 全量回灌，bugfix 不受灰度控制）；门 2 是 `validity.tieringEnabled` 灰度闸（默认关）；门 3 是 `memory_search` 的三个反查参数 `include_expired` / `as_of`（按有效期回放，退场的不复活）/ `follow_supersede`（顺取代链 0–5 代并反查被谁取代），默认全关。

### 淡出，而不是淘汰

召回排序里有一层衰减：`score × max(0.5, 0.5 ** (days / halfLife))`，半衰期默认 30 天，**地板 0.5**——老记忆最多损失一半排序分，永不沉底。注释特意说明这是乘法、保相关性主导，"只在相关度相近的候选之间轮转名次，不淘汰不硬过滤"；而且**去重候选池不得应用衰减**，否则会让去重漏检。

还有几类"遗忘"更机械：常驻槽位和技能都有 `expireDue` / `archiveDue`，由调用时机机械触发、零 LLM、不引定时器；人在召回卡上给一条记忆打 -1「声明过时」，会**同时**做两件事——退场该记录，并往 outbox 排一条下一轮的一次性播报（"这几条刚被判定过时、已从记忆库退场，别再依据它们作答"，单轮最多 8 条）。这条播报是必要的：模型此刻的上下文里那条记忆**还在**，不显式告知就会继续引用它。

**覆盖写本身也是一种遗忘**。L2 场景和 L3 画像都是整份重写，旧措辞自然消亡；反刍还会做重新标注与场景重聚类，把被合并取代的记录从没改名的文件上挪走。捕获侧则更前置：L0 停写 + 脱敏，等于从源头就决定"原文不留下"。

本机库里 665 条 L1 记录中有 **271 条已退场**（约 41%），大多是去重取代留下的历史版本。这个比例本身就说明：在这套设计里，"被取代"是常态，不是异常。

## 7. 冲突解决：从自动去重到人工裁决

冲突处理分两条路，一条默认开、一条默认关。

### 默认路径：L1 去重时顺手解决

新卡片入库前，先拿它的 content 去**同族候选池**里召回相似旧记忆（候选池只在本族内，永不跨族），再把"新记忆 + 统一候选池"一起交给一次 LLM 批量判定，四选一：

| 动作 | 含义 |
| --- | --- |
| `store` | 视为新信息，新增 |
| `skip` | 已有记忆更好、无增量，丢弃本条 |
| `update` | 同一事实，新的更具体/更晚/是纠错，覆盖旧 |
| `merge` | 互补不矛盾，合并成更完整的一条 |

判定看主体、主题、时间与场景名是否指向同一件事；状态类（偏好、指令）和事件类（经历）判法不同；支持跨 type 合并、多对多合并（target_ids 是数组），合并后重新判最佳 type、酌情提升优先级，时间戳取并集去重排序。

`update`/`merge` 的落地是：旧记录的 id 记到"被谁取代"映射里（取首个取代者、与退场幂等一致）→ 造一条带合并内容、继承旧身份的新记录 → 旧记录带 `reason: 'superseded'` 和 `by: 新 id` 退场 → 图谱把旧源支撑的边标墓碑并重投。**所以"解决冲突"在最常见的情况下，就是一次带取代链的软删 + 新增。**

还有一层很值得学的东西：**决策凭证**。每一轮去重都会为**全部**抽取结果（包括 `skip` 的和"模型压根没返回决策"的）留一条凭证，记下当时的候选池输入摘要与结论，可按记录问"这条出自哪一轮、当时看到什么候选池"，也可按批次问"那一轮都判了什么"。注释里那句理由是硬道理：**凭证必须在事件之前存在——输入快照无法事后补录**。这是"记忆系统自己也要可审计"的一个漂亮落点。

### 可选路径：矛盾冻结，把裁决权交还给人

默认去重是让模型自己判输赢。但有些矛盾不该由模型拍板，于是有个 `conflictFreeze` 开关（**默认关**）。开启后，去重 prompt 会多注入一个 `conflict` 动作；命中时：

> **新记忆照常入 L1**，与它冲突的旧记忆**作为一对**停进待裁决队列，**双方内容都不被改写**，直到人来裁决。

项目对这条语义的注脚引了另一套系统的说法："dream layer does **NOT** auto-adjudicate winner/loser — the conflicting pair is parked here until a human reviews it." 并且特意澄清：冻结**不是"拦住写入"，而是"不自动裁决"**。默认关的理由也很实在——"冻结消耗人的注意力，不可默认全开"。

人工裁决有四个结论：`winner`（采纳建议的胜方，败方退场）、`loser`（反过来）、`both`（判定两者是各自独立的事实，都保留）、`defer`（看过但暂不裁决，重置超时计时并累计复看次数）。裁决的实现顺序是**先打 `resolved_at` 再退场败方**，打标用 `WHERE resolved_at = ''`，天然防重复裁决；退场后重算图谱的争议集。于是有个很有意思的性质：

> **裁决不可覆盖，但可以反悔。** 判错了不能改判（第二次裁决直接返回"该对已被裁决，本次未生效"），但败方是软删、可恢复。

安全阀也配齐了：队列上限 100（语义是"**不收新的**"，不是"偷偷删旧的"）；超过 30 天未裁决的对自动了结，但**仍写进队列、只是 `resolution='auto'`**——"痕迹必须留下"；`defer` 累计 3 次后不再被超时自动了结、只能人工收口（fail-loud）；队列满时若败方恰好是本轮刚抽出的新记忆，**不做自动了结**（否则刚产出的东西立刻退场且无人知晓）；只有 `hard` 类冲突占额度，`conditional` / `supersession` 不占但越界要告警；配不成对的畸形决策回落到 `store` 并单独留痕。读侧还有一组只帮人、不参与自动了结的辅助信息：有效期/持续性三轴、成熟度（按优先级/使用/时效/反馈算）、冲突类型与 claim 键分组。

本机这两个开关都关着，所以待裁决队列、冲突留痕、图谱节点实测都是 0——下面这条边界得说清楚。

## 8. 边界：这套结论在哪儿失效

写完机制，得把可信范围钉住：

- **版本锁定**：以上是 0.26.29 的实现，装在桌面 profile 上。换版本、换 profile、换部署配置，事件缝与开关状态都要重验。
- **血缘**：它不是"碰巧像" TencentDB Agent Memory 的四层语义金字塔，而是照 **MemoryCore 长期记忆管线**做的单机移植 + 改写。项目自己列了四条差异：内嵌完整管线不依赖外部网关、蒸馏复用宿主自己的 LLM；L2/L3 从"LLM 操作文件工具"改成"LLM 输出操作 JSON / 完整文档、工程侧执行"；召回注入点用 `agent/pre-step` + agent 作用域的系统提示段位；存储检索是官方 SQLite 后端的单机裁剪版（裁掉多租户隔离列、云后端与审计表，分词仍与官方一致用 jieba + CJK 二元组并集）。**短期上下文压缩不在这套移植里**，由另一个 bundle 承担。
- **本机当前状态是"部分停摆"，别当成设计缺陷**：写这篇时，L1 抽取的模型调用连续撞 120 秒超时被中止，累计失败 63 次后进入 1800 秒暂停重试，待重试 177 条。因此近几轮没有新 L1，L2/L3 的更新时间停在 11-05，画像与场景都是存货。**捕获与召回是好的**（这轮对话开头注入的那几条记忆就是证据），坏的是后台蒸馏那一段。
- **默认关的能力**：图谱、矛盾冻结、时效分层灰度、有效性分级都在关闭态。上面第 4、7 节里那些表与队列是"设计好了、可打开"，不是"正在跑"。本机 `graph_nodes=0`、`conflict_pending=0`。
- **封面代价**：按指定素材原样使用，图是 1200×600（2:1）的 SVG，没有做 1600×900 合成；主题封面容器接近 16:9，可能会有轻微上下裁切。矢量图缩放不失真，但构图边缘有被切的风险，观感仍以页面实际渲染为准。

## 9. 小结

把这一整套收成三句话：

1. **接入方式**是进程内事件缝，不是外部命令钩子：一条 `session/event` 负责捕获、一条 `agent/pre-step` 中间件负责前置注入、一个系统提示段位负责稳定区，加上工具注册与 RPC 面板。
2. **记忆形态**是三次不同形状的 LLM 问答：L1 抽出带依据与范围的原子事实，L2 把新事实并进整份场景文档，L3 从变化场景蒸出整份画像；族划共享面、类型划标签、图谱只是 L1 的派生投影。
3. **遗忘与冲突**都押在同一条原则上——**可逆优先、人留最后一步**：退场是撤索引不是删行，修订是加版本不是覆写，冲突默认由模型去重解决、真有争议就冻结起来等人裁决，且裁决不可覆盖但可反悔。

如果说这套实现里最值得抄的是哪一点，我选"**单一写面真源 + 每条决策都留凭证**"：所有派生结构（文件、场景、画像、图谱）都能顺藤摸回一条现存记录，所有自动判断都能回答"当时看到了什么"。代价也很具体——增量一致性的账本一旦用计数器近似，就得靠后台全量兜底来补；而后台兜底什么时候跑，目前还得人去推一把。

记忆系统最难的部分从来不是"存下来"，而是**在你要改主意的时候，它还允许你改**。这一点它做得比大多数方案都认真。
