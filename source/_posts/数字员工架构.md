## 0. 先换一个问题：它不是"写什么提示词"，而是"它住在哪"

接触过几个团队之后我发现，大家做数字员工卡住的地方几乎一模一样：**不是模型不够聪明，是没想清楚这个东西"住在哪、谁守着它、它干了一半崩了怎么办"。**

写提示词是"它这次干活时脑子里想什么"，属于最容易的部分。真正决定成败的是另外几个问题：

- 这个员工常驻在哪？是一个进程、一个容器，还是一段被调用的函数？
- 没人给它派活的时候，它在哪待着？
- 它干到一半进程被重启，活儿会不会丢？
- 它明天、下个月还记不记得今天定过的口径？
- 它出错的时候，你怎么知道它到底动了哪些数据？

这些问题的答案，合起来就是"架构"。下面从最容易含糊、也最该先讲清楚的一个词开始：宿主。

## 1. 先对齐视角：同一件事的三种说法

| 视角 | 关心什么 | 对应到架构 |
| --- | --- | --- |
| 老板 / 业务方 | 这个人负责什么、不能干什么、交付什么 | 岗位定义、边界、交付物 |
| 使用者 | 我一句话丢过去，它自己去找、自己判断 | 入口、上下文装配、工具 |
| 机器 | 一份定义 + 一个宿主 + 一份状态 + 一组能力 + 一组触发 | 五层骨架 |

工程上只认第三种，但前两种必须被**翻译**进第一种——翻译不了的，就是需求没想清楚。

## 2. 宿主到底是什么

### 2.1 一句话定义

**宿主（Host）是"把一份员工定义，变成一个可被派活、可被观察、可被恢复的运行体"的那段程序。**

拆开看这句话里的三个词：

- **可被派活**：它对外有一个入口，别人能把任务丢进来，而不是只能打开一个聊天框手动说话。
- **可被观察**：任务进行到哪一步、调了什么、产出了什么，外部能看见，而不是只有一个黑盒的最终回答。
- **可被恢复**：进程死了，任务不跟着死；换个进程接着跑，还能知道之前做到哪。

### 2.2 它不是什么

这三个"不是"能省掉很多返工：

- **不是模型。** 模型只负责"这一轮该怎么想、要不要调工具"。宿主负责"这一轮之外的一切"。
- **不是业务代码。** 宿主管的是通用的运行机制（装载、装配、循环、落盘、代理），业务规则应该写在定义、能力、流程里。一旦宿主里出现 `if (客户是某某) `，它就不再通用了。
- **不是提示词。** 提示词是定义层的一个字段（可能就是 `system.md` 一个文件），宿主只是把它读进来放进上下文。

### 2.3 它的六个职责

一个合格的宿主，内部大概是这样：

| 职责 | 具体做什么 | 少了它会怎样 |
| --- | --- | --- |
| 装载 | 读 manifest、校验字段、注册能力、检查版本 | 员工定义散落在代码里，加一个人改一次代码 |
| 装配 | 按员工定义拼出这次请求的上下文 | 每次都要人工贴背景，行为不可复现 |
| 代理 | 替模型真正执行工具，管权限、凭据、审计 | 模型直接拿到高权限凭据，出事查不到人 |
| 循环 | 多轮"想—调—看结果—再想"，判停 | 只能一问一答，干不了需要多步的活 |
| 状态 | 把任务、产物、记忆写下去，能恢复 | 进程一重启，活儿全丢 |
| 接口 | 对外暴露接活/观察/恢复 | 只能人工点按钮，接不进别人的系统 |

### 2.4 宿主的三种形态

同一个宿主，在不同规模下长得很不一样，但**接口应该一样**：

| 形态 | 长什么样 | 适合 | 代价 |
| --- | --- | --- | --- |
| 进程内库 | 你的服务 `import` 一个包，`host.dispatch()` 完事 | 自用工具、内部单机 | 一个员工崩了可能带走主进程 |
| 独立子进程 | 宿主被拉起成独立进程，跑完即退 | 需要故障隔离、CPU 活重 | 启动开销、进程间通信 |
| 常驻服务 | HTTP 服务 + 任务队列 + 执行器池 | 多租户、多员工、要弹性 | 复杂度最高，运维成本跟着涨 |

**选型标准只有一条**：员工包里会不会出现"别人的代码"（客户自建、第三方包、MCP 连接）。会，就必须走到独立进程或更强隔离；不会，进程内库最省事。

### 2.5 最小宿主长什么样

宿主听着玄，落到代码上其实很小。一个能跑通的最小实现，核心就这些方法：

```ts
interface Host {
  // 装载：读定义、校验、注册能力。失败要能说清是哪一条不合格。
  open(def: EmployeeDef, deps: Deps): Promise<Host>;

  // 接活：只落库、返回任务号，不等执行。接口应该是"提交"而不是"执行"。
  dispatch(input: DispatchInput): Promise<TaskId>;

  // 干活：从状态里恢复出上下文，跑循环，提交结果。可以被任意进程调用。
  run(taskId: TaskId): Promise<Outcome>;

  // 恢复：扫出所有"卡在 running 的任务"，按租约与重试上限决定续跑还是判死。
  resume(): Promise<RunReport>;

  // 观察：订阅任务事件（阶段、工具调用、产物），前端/人靠它知道进展。
  observe(taskId: TaskId): AsyncIterable<HostEvent>;
}
```

注意这几个方法的形状，每一个都对应一条设计约束：

- `dispatch` 返回 `TaskId` 而不是结果 —— 因为执行可能几分钟，接口不能阻塞；也因为**任务必须先落库**。
- `run` 只吃一个 `taskId`，不吃上下文对象 —— 因为上下文应该从状态里重建，而不是从调用方内存里传。
- `resume` 是独立方法 —— 恢复不是"启动时顺手做的事",它是常态路径，得有单独的入口和报告。
- `observe` 是流 —— 因为"干到哪了"本身就是产品的一部分。

至于里面那圈循环（调模型、解析工具调用、判停），那是**引擎**的活。宿主 = 引擎 + 定义 + 状态 + 能力代理。换个引擎，宿主的上半部分不用动。

### 2.6 四个东西的边界别搞混

新手最容易把"宿主"和"引擎"混成一个词，于是所有东西都往一个类里塞，最后变成一个三千行的上帝对象。四个概念的分工：

| 东西 | 一句话 | 换它意味着什么 |
| --- | --- | --- |
| 员工定义 | 这个人是谁、干什么、交付什么 | 换人，不动系统 |
| 引擎 | 一轮决策怎么想、怎么调工具 | 换模型供应商、换实现，员工行为风格会变 |
| 宿主 | 把定义装起来，管状态、管能力、管接口 | 换部署形态（函数 / 进程 / 服务） |
| 执行器 | 真正跑 `run()` 的那个进程或容器 | 扩容、换机器、迁移，都是它的事 |

一个检验方法：**你换掉其中一样，其他三样要不要改？** 换引擎不用改定义、不用改任务表，那说明边界划对了；换引擎要改一半代码，说明引擎的职责漏进了宿主。

### 3.1 定义层：员工是一份可版本化的资产

六个必填维度：岗位、职责、边界、能力、记忆、交付物。落到文件上：

```yaml
id: after-sales-analyst
name: 售后数据助理
version: 0.3.0
owner: 售后负责人

responsibility: |
  负责退款与售后数据的拉取、日/周复盘、异常波动定位。
boundaries:
  - 不改价、不发券
  - 不对外发送任何消息
  - 涉及金额口径变化必须找人确认

capabilities:
  tools: [db.readonly, ticket.query, report.render]
  knowledge: [口径手册, 历史复盘]
  connectors: [ticket-system]

deliverables:
  - id: report
    format: markdown
    required_sections: [结论, 数据来源, 口径说明]
  - id: summary
    format: text
    max_chars: 200

memory:
  always: [退款口径, 客户禁忌]
  relevant: [历史结论, 同类异常案例]
```

判断这份定义好不好，看一条：**换一个宿主、换一个模型、换一台机器，它还是同一个员工吗？** 如果某条规则只写在宿主的代码里，那它就不属于这个员工。

### 3.2 宿主层

见第 2 节。这里只补一句：宿主的代码量应该和员工数量**无关**。宿主变胖，通常是员工定义没写全，业务逻辑漏到了运行时。

### 3.3 能力层：越可控越好，不是越多越好

能力分四类，管理方式完全不同：

| 类型 | 例子 | 关键约束 |
| --- | --- | --- |
| 工具 | 查库、渲染报表、发工单 | 参数校验、权限、超时、幂等 |
| 知识 | 口径手册、历史复盘 | 检索质量、来源可追溯 |
| 连接器 | 客户 CRM、工单系统 | 凭据保管、限流、字段映射 |
| 凭据 | 数据库只读账号、API Key | 短时、最小范围、可轮换 |

工具不能直接"注册一个函数给模型"。正确形态是一份**能力声明**：

```json
{
  "name": "db.readonly",
  "description": "对售后库执行只读查询，只能访问 refund、ticket 两张表",
  "input_schema": { "sql": "string" },
  "effects": "read",
  "auth": { "secret": "after-sales-db", "ttl_seconds": 300 },
  "limits": { "calls_per_run": 20, "timeout_seconds": 30 },
  "approval": "never"
}
```

每一条都能被机器执行、被人审阅：`effects` 决定崩溃恢复时允不允许重跑，`auth` 决定凭据给多长、多大范围，`limits` 决定它不能把配额吃光，`approval` 决定要不要人点头。

### 3.4 状态层：员工的连续性全在这里

状态层至少要有五张东西：

| 状态 | 存什么 | 不做会怎样 |
| --- | --- | --- |
| 任务 | 任务号、状态、输入、每次尝试、租约 | 崩了不知道有活没干完 |
| 会话历史 | 消息序列、工具调用与结果 | 第二句话就开始失忆 |
| 记忆 | 结论、口径、偏好，分 always/relevant | 每次都重新交代一遍 |
| 产物 | 文件、报表、链接 | "做完了"但没人知道东西在哪 |
| 审计 | 谁、用什么能力、改了什么、什么时候 | 出事查不出原因 |

关键是**任务状态机要闭合**。状态少一个，"卡住"的任务就会永远卡住：

  B --> C{"执行中"}
  C -->|"正常结束"| D["完成 done"]

### 3.5 触发层：谁把它叫醒

三种触发，实现方式各不相同：

- **人**：接口 / 聊天入口。最简单，也最容易被当成全部。
- **时间**：定时器只生成一条待办记录，不负责执行。
- **事件**：webhook、消息、数据变化。要防重放，也要防事件风暴。

一句话原则：**触发层只产生"要干这件事"的记录，绝不亲自干活。** 这条一破，后面所有关于"崩了怎么办"的设计都白做。

## 4. 一条主链路

{% mermaid %}
sequenceDiagram
  participant T as 触发源
  participant H as 宿主
  participant S as 状态层
  participant M as 模型
  participant K as 工具与外部系统
  T->>H: 派活（指令 + 输入）
  H->>S: 落任务记录 queued
  H->>S: 读记忆、知识、历史
  H->>M: 请求（岗位提示 + 上下文 + 能力清单）
  M-->>H: 意图 + 工具调用
  H->>K: 执行（权限校验 + 短时凭据）
  K-->>H: 结果（截断后回填）
  Note over H,M: 不够就再来一轮
  H->>S: 提交产物与状态
  H-->>T: 交付说明
  H->>S: 沉淀记忆/经验
{% endmermaid %}

每一步的输入输出：

| 步骤 | 输入 | 输出 | 失败怎么办 |
| --- | --- | --- | --- |
| 派活 | 指令、文件、上下文引用 | 任务号 | 校验不过直接拒绝，不落库 |
| 装配 | 任务 + 记忆 + 知识 + 历史 | 一次请求的上下文 | 超预算就裁剪，不报错中断 |
| 决策 | 上下文 + 能力清单 | 文本或工具调用 | 模型报错按可重试/不可重试分流 |
| 执行 | 工具名 + 参数 | 结果或错误 | 超时/失败回填给模型，不抛出中断 |
| 提交 | 产物 + 状态变更 | 新状态 | 一个事务里写完，不写半截 |
| 通知 | 交付说明 | 消息/回调 | 通知失败不影响任务状态 |

两条铁律，违反任何一条都会在半年后以"玄学 bug"的形式还回来：

1. **先落库，再干活。** 任务记录必须在模型第一次被调用之前写下去。
2. **先提交，再通知。** 产物进状态层之后才通知人。反了就会出现"人看到了结果，但系统里没有"。

### 4.1 展开：一次派活，宿主内部走了哪几步

时序图看的是"谁和谁说话"，实际落地时更该关心"每一步往状态层写了什么"。把一次派活摊开：

| # | 宿主动作 | 写入状态层 | 失败时 |
| --- | --- | --- | --- |
| 1 | 校验输入（员工是否存在、参数是否合法） | 不写 | 直接拒绝，不产生任务 |
| 2 | 建任务，状态 `queued` | 任务行：输入、员工版本、创建者 | 写失败就返回错误，别继续 |
| 3 | 执行器领活，状态 `running`，写租约 | 租约持有者、到期时间、尝试次数 | 领不到就等下一轮，不抢 |
| 4 | 装配上下文（系统提示 + 记忆 + 知识 + 历史） | 记录本次用了哪些记忆/知识（可追溯） | 超预算就裁剪，不中断 |
| 5 | 记 `request/header`：本次能力清单快照 | 能力清单、模型、参数 | — |
| 6 | 调模型 | 不写（还没产生事实） | 可重试的退避重试，不可重试的直接失败 |
| 7 | 模型要调工具：校验参数 → 判权限 → 扣配额 | 调用意图（含参数、effects、幂等键） | 校验不过就把错误回填给模型，不抛出 |
| 8 | 真正执行工具（短时凭据） | 结果摘要 + 耗时（大结果落盘只存引用） | 超时/报错回填给模型，让它决定下一步 |
| 9 | 循环 6–8，直到模型不再调工具 | 每轮增量写，不攒到最后 | 达到轮次上限就收尾并标注原因 |
| 10 | 校验交付物（必需章节、格式、长度） | 不合格就在同一次执行里重做 | 连续不合格 → `failed` 并说明 |
| 11 | 提交产物与终态 | 产物、最终状态、结束原因 | 一个事务写完，不写半截 |
| 12 | 通知 + 沉淀记忆 | 记忆条目、经验、审计 | 通知失败只重试通知，不动任务状态 |

这张表有三个用处：

- 它是**恢复逻辑的规格书**。每一行都告诉你"崩在这一步，重启后该从哪继续、哪些可以安全重来"；
- 它是**状态机的实现清单**。表里出现的每一种写入，都要有对应字段；
- 它是**排查问题的地图**。任务卡住时，先看它停在第几步，比翻日志快得多。

特别注意第 7 步和第 8 步是分开的：**先落"我打算调这个工具"的意图，再真去调。** 这样即使在第 8 步崩溃，恢复时也知道"有个动作可能已经发出去了"，而不是完全不知道自己干到哪。

## 5. 四个决定成败的设计决定

### 5.1 定义与运行分离

**为什么**：员工要能升级、复制、迁移、按客户定制。这些能力全都要求"定义是数据"。

**怎么做**：定义以文件/包形式存在，宿主只做解释；定义里出现"如果客户是 A 则……"，把它挪到能力配置或流程配置里，而不是塞进代码分支。

**做错的样子**：每加一个员工就要改一次宿主代码、发一次版。员工数到十几个，宿主里全是 `if (id === 'xxx')`。

**怎么验证**：新加一个员工，需要改代码吗？需要，就说明分离没做到。

### 5.2 状态外置，执行器可替换

**为什么**：这是"数字"两个字的分量。执行器是消耗品，状态才是资产。

**怎么做**：
- 每次执行 = 从状态层恢复 → 干活 → 提交回状态层；
- 任务带**租约**（lease）：领活时写"我持有到某时刻"，执行中定期续，过期就允许别人接管；
- 重试要有上限，并且**按任务累积**而不是按进程累积（否则每次重启都清零，死循环）；
- 工具要标 `effects`：只读的允许重放，有副作用的恢复时写成"可能已部分执行，请人工确认"，绝不自动重放。

**做错的样子**：进程重启后，任务永远停在 `running`；或者一次超时重试，客户收到两张券。

**怎么验证**：在工具执行到一半时 `kill -9`，重启后看任务是被正确接管，还是永久卡死。

### 5.3 能力：声明与执行分离

**为什么**：模型不该直接握着高权限凭据。它决定"要做什么"，但不该决定"能碰什么"。

**怎么做**：
- 宿主登记能力清单：名字、参数、effects、权限、限额、审批要求；
- 模型只能按清单发起调用，参数先校验；
- 宿主判权限、扣配额、记审计，然后才真正执行；
- 真正执行的那一刻才下发**短时、限定范围**的凭据。

**做错的样子**：把一把管理员 token 塞进环境变量，所有工具共用；出了事只能查"这个员工动过"，查不出"哪一次、用什么身份、改了哪一行"。

**怎么验证**：随便挑一次工具调用，能不能回答四个问题——谁发起的、用的什么身份、碰了哪些数据、失败了会不会重放。

### 5.4 触发与执行解耦

**为什么**：定时任务最常见的错写法是"起个常驻进程，到点叫醒"。进程一挂，任务静默消失；多实例一开，同一个任务执行两遍。

**怎么做**：
- 定时器只生成 **occurrence 记录**：`(automationId, triggerId, triggerRevision, fireTime)` 做唯一键，重复生成只会冲突不会重复执行；
- 错过触发要有明确策略：跳过、补一次、还是全补；
- 同一自动化并发要有策略：排队、跳过、还是顶掉；
- occurrence 落库时冻结当时的配置快照，改了配置不影响已经在跑的那次。

**做错的样子**：改了一条定时任务的配置，结果昨天已经在跑的那次也跟着变了行为；或者服务扩容到两个副本，客户每天收到两条日报。

**怎么验证**：把执行器开两个实例，观察同一时刻的任务会不会被执行两次。

## 6. 让它越干越好：记忆、知识、技能、评测

前面讲的都是"能不能跑"。这四件决定"好不好用"。

### 6.1 记忆要分级，而且要会忘

不是把所有历史塞进上下文，而是分两类：

| 类型 | 内容 | 预算 | 写法 |
| --- | --- | --- | --- |
| `always` | 口径、禁忌、关键偏好 | 少而硬，比如 20 条 / 8000 字符以内 | 直接进系统提示 |
| `relevant` | 历史结论、同类案例 | 多而软，按相关性检索 | 检索后取 top-k，带来源 |

三个实操点：

- **写入时机**：任务结束、人明确纠正、人明确要求记。别在每轮对话里自动写，噪音会淹没信号。
- **冲突处理**：新记忆与旧记忆矛盾时，不要覆盖，标记旧的失效并留痕——"为什么改口径"本身是重要信息。
- **遗忘**：定期把长期没被检索到的记忆降级/归档，否则一年后每次请求都在为三个月前的寒暄付 token。

### 6.2 知识要可追溯

知识库不是"把文档丢进去"。每条知识至少要能回答：来自哪份文档、哪一版、什么时候。否则员工给出的结论你没法复核，也就没法信任。

### 6.3 技能要沉淀成 SOP

同一件事干到第三次，就该变成一份固定步骤（甚至一段脚本），而不是每次让模型重新想。

判断标准很朴素：**这次的做法，下次还需要模型再想一遍吗？** 不需要的，就该固化。

### 6.4 验收要有尺子

没有评测的数字员工，你永远不知道它这次是运气好还是真的会。最小可行做法：

1. 准备 10–20 个真实任务，人写好"合格交付物"长什么样；
2. 每次改提示词、换模型、加能力，跑一遍；
3. 看两个数：**完成率**（能不能交付）与**合格率**（交付物对不对）。

这两个数不上去，加再多能力都是自我感动。

| 维度 | 单人自用 | 小团队 | 对外产品 |
| --- | --- | --- | --- |
| 状态 | SQLite 单文件 | Postgres | 独立存储 + 备份 |
| 执行 | 主进程内 | 独立 worker | 执行器池 + 沙箱 |
| 触发 | 手动 + 简单定时 | 队列 + 定时 | 队列 + 事件总线 |
| 隔离 | 不需要 | 进程级 | 容器/租户级 |
| 观测 | 日志 | 日志 + 任务面板 | 全链路追踪 + 审计 |

三处不同，骨架不变。**骨架一改，就是另一个系统了**——这也是为什么第 2 节要把宿主接口定死。

## 8. 八个常见的坑，以及怎么解

### 8.1 把会话绑在进程上

- **症状**：会话一多就要起一堆常驻进程；机器一重启，所有会话上下文全丢；想扩容只能拆机器。
- **根因**：会话状态存在进程内存里，进程成了会话的宿主。
- **解法**：状态外置，执行器无状态。会话是存储里的一条记录，执行器只做"读出来—干活—写回去"。热路径用预热池降低恢复成本，但**正确性不依赖常驻**。

### 8.2 定时任务做成常驻进程

- **症状**：服务重启后有几天的任务没跑；扩容到两个副本后，客户每天收到两封邮件。
- **根因**：触发和执行耦合在一个进程里，既没有持久化的待办记录，也没有唯一键去重。
- **解法**：定时器只写 occurrence 记录（唯一键 = 自动化 + 触发器 + 版本 + 触发时刻），执行器领活；明确"错过怎么办""并发怎么办""配置改了跑着的那次算谁的"。

### 8.3 能力裸奔给模型

- **症状**：所有工具共用一个管理员凭据；出了事故只能查到"这个员工动过数据库"。
- **根因**：能力注册等于"把函数挂上去"，没有声明、没有权限层、没有审计。
- **解法**：能力清单 + 网关式执行 + 执行时下发短时凭据 + 每次调用记审计（谁、什么能力、什么参数摘要、结果摘要）。

### 8.4 重试不幂等

- **症状**：客户收到两张券；报表里同一天的数据翻倍。
- **根因**：网络超时后重试，动作实际已经执行成功。
- **解法**：写操作带幂等键，由被调用方或一层薄的"动作表"去重；工具声明 `effects`，恢复时只重放只读的。

### 8.5 记忆无限膨胀

- **症状**：请求越来越慢、越来越贵；模型开始被三个月前的无关细节带偏。
- **根因**：所有历史都进上下文，没有分级、没有预算、没有遗忘。
- **解法**：`always` / `relevant` 分级；给记忆一个明确的字符预算；定期归档长期未命中的条目；冲突时标记失效而非覆盖。

### 8.6 交付没有契约

- **症状**：员工说"已完成"，但没人知道东西在哪、算不算完成。
- **根因**：定义里没写"交付物长什么样"，验收全靠人肉看。
- **解法**：定义里给交付物 schema（必需章节、格式、长度），宿主在提交前做一次结构校验；不合格就退回重做，而不是直接通知人。

### 8.7 崩溃后任务永远卡在 running

- **症状**：后台有一批任务状态是 `running`，但没有任何进程在跑。
- **根因**：只做了"崩溃前写 running"，没做"崩溃后回收"。
- **解法**：租约 + 心跳 + 超时回收 + 重试上限。恢复逻辑要能被定时触发，而不是只在启动时跑一次。

### 8.8 上下文没有预算，被工具结果撑爆

- **症状**：某个工具返回了 20 万字符的日志，这一轮直接超限报错，或者模型开始胡说。
- **根因**：上下文装配没有预算概念，工具结果原样回填。
- **解法**：给上下文分预算（系统提示 / 记忆 / 知识 / 历史 / 工具结果），工具结果超限先截断再回填，大结果落盘、只回一个引用和摘要。

## 9. 落到具体引擎

上面讲的是设计，不是实现。真写代码时，通用引擎已经替你做掉了一部分，剩下的是你补：

| 骨架模块 | 引擎通常能替你做的 | 你还得自己做的 |
| --- | --- | --- |
| 决策循环 | 多轮循环、工具调用解析、重试、中止 | 岗位提示怎么写、什么时候该停、停了之后算成功还是失败 |
| 会话与状态 | 消息持久化、会话树、断点恢复 | 任务表、业务状态机、产物存放、租约回收 |
| 能力接入 | 工具注册、参数校验、MCP 接入 | 权限、审批、配额、凭据轮换、审计 |
| 记忆 | 存原始对话 | 分级、检索、写入时机、遗忘与冲突 |
| 触发 | 基本不管（这是最容易被低估的一块） | 定时、事件、去重、错过策略、并发策略 |
| 隔离 | 进程内 / 子进程 / 沙箱可选 | 按员工风险等级选级别，并想好降级方案 |

落地节奏我一般这么排：

- **第一天**：跑通一条链路——定义 → 装配 → 循环 → 一个只读工具 → 落库。别碰多员工、别碰定时。
- **第一周**：补状态机（queued/running/waiting_input/done/failed）、租约回收、产物落盘、一个最简单的审批。
- **第一个月**：补记忆分级、能力清单与审计、定时触发与幂等、十来个金标任务的评测。

## 10. 小结：三条边界

设计一个数字员工，本质上是在划三条边界：

- **它是谁**：岗位、职责、边界、能力、交付物。这是资产，必须数据化，必须能版本化。
- **它怎么活**：宿主 + 状态 + 触发。这是运行时，必须可替换、可崩溃、可恢复。
- **它怎么变好**：记忆分级、技能沉淀、验收评测。这是运营，必须能迭代。

框架可以换，引擎可以换，这三条边界不能含糊。把边界划清楚，剩下的就是选一个顺手的引擎，把五个格子填满——不管选哪个，填的都是同样的五个格子。
