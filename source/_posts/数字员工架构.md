## 0. 先说三个现场

**第一个现场：上线两周，没人用。** 不是不好用，是没人知道怎么"派活"——它只有一个聊天框，业务方要传三个附件、说明这次是哪张单子，传完还得盯着它别跑偏。从头到尾没有"提交一个任务"的入口。

**第二个现场：半夜告警。** 一个大客户的对账任务卡在 `running` 四个小时。查下来是进程在第三步被 OOM 杀掉，任务记录还停在"执行中"，没有任何东西会把它捡起来。

**第三个现场：同一笔退款发了两遍。** 原因很朴素——工具调用超时重试，而退款接口不幂等。

三个现场对应三件完全不同的事：**入口、恢复、幂等**。它们都不在提示词里。

这也是我写这篇的原因。数字员工最容易被误解成"一段更长的提示词 + 一个聊天框"，而真正让人返工的，全是提示词之外的东西。下面按**你必须做的八个决定**来组织，每个决定都按同一个套路说清楚：

> 它在解决什么 → 有哪几种做法、各自的代价 → 我建议哪种、为什么 → 做错长什么样 → 一行验收。

八个决定依次是：它是什么形状的资产、谁来跑它、它凭什么知道该干什么、它能碰什么、谁叫醒它、崩了丢不丢活、你怎么知道它干得对、怎么装第一百个。

先给一句话的答案：**数字员工 = 一份可版本化的定义 + 一条记录着身份与记忆的实例 + 一次短命的运行。** 剩下的七个决定，都是围绕这三件东西展开的。

## 1. 决定一：它是什么形状的资产

这个决定排第一，因为它决定了后面所有事。选错了形状，后面每一条都在跟形状打架。

我见过三种典型的长法，三种都在某个规模上崩掉：

| 长法 | 一开始很方便 | 崩在哪 |
| --- | --- | --- |
| **提示词仓库** | 一段 system prompt，复制一份改改就是新员工 | 没有身份、没有记忆、没有权限边界；十个员工十个孤立提示词，改一次口径要改十处 |
| **代码里的分支** | 用 `if (employeeId === 'xxx')` 写差异化逻辑 | 加一个员工改一次代码、发一次版；二十个人之后没人敢动宿主 |
| **一个进程一个员工** | 起个进程，进程活着员工就活着 | 进程是消耗品，员工却不是；扩容、迁移、灰度、崩溃恢复全都变成运维题 |

正确的形状是把一个员工拆成三件东西，**分开存、分开改、分开失效**：

三者的边界：

| | 定义 | 实例 | 运行 |
| --- | --- | --- | --- |
| 是什么 | 一段可安装、可版本的配置与代码 | 一个具体的员工（"售后专员-华东-01"） | 一次从唤醒到交付的执行 |
| 存哪 | 包仓库 / 版本库 | 数据库一行 | 进程内存 + 持久化日志 |
| 生命周期 | 长（跟随发布） | 长（跟随员工在职） | 短（分钟到小时） |
| 谁改它 | 开发者发版 | 管理员/业务方调参 | 没人改，只有产出 |
| 崩了会怎样 | 无影响 | 无影响 | 这次执行重来 |

这个拆法带来三个立刻可用的推论：

1. **改一句岗位说明不等于重启进程。** 它是一次版本变更，下次唤醒生效即可。
2. **"员工在线/离线"不是架构状态。** 它只是实例记录上的一个字段，跟有没有进程在跑无关。
3. **迁移、复制、灰度都是实例操作。** 复制一个员工 = 复制一条记录并指向同一个定义版本，不需要复制代码。

**做错的样子**：你为了给某个客户改一段提示词，不得不改代码、发版、重启服务。

**一行验收**：新增一个员工，需要改代码吗？需要，形状就错了。

## 2. 决定二：谁来跑它

定义是包，实例是记录，那么"跑"这件事落在谁身上？答案是一个**运行体**——平时大家管它叫宿主（Host）、运行时、执行器，叫什么都行，关键是想清楚它到底承担什么、不承担什么。

### 2.1 它只做三件事

一句话：**运行体是把"一份定义 + 一条实例"变成"一次可被观察、可被恢复的执行"的那段程序。**

- **可被派活**：对外有提交入口，别人能把任务丢进来，而不是只能有人坐在聊天框前。
- **可被观察**：进行到哪一步、调了什么、产出了什么，外部看得见，而不是只有一个最终回答。
- **可被恢复**：进程死了，这次的活儿不跟着死；换个进程接着跑，还知道做到哪。

反过来，三件事**不该**由它做：

- **它不是模型。** 模型只决定"这一轮怎么想、要不要调工具"，运行体负责这一轮之外的一切。
- **不是业务代码。** 一旦里面出现 `if (客户是某某)`，它就不再通用了，这种分支应该落到定义或能力配置里。
- **不是打包器。** 员工包从哪来、谁装、怎么升级、两个员工要不同版本怎么办——这是交付层的事（见决定八），塞进运行体会把它变成一个包管理器。

### 2.2 三种形态，选错了很难改

| 形态 | 长什么样 | 适合 | 代价 |
| --- | --- | --- | --- |
| **进程内库** | 你的服务 `import` 一个包，调 `dispatch()` | 自用工具、单人单机 | 员工崩了可能带走主进程 |
| **独立子进程** | 拉起一个进程跑完即退 | 需要故障隔离、CPU 活重 | 启动开销、进程间通信 |
| **常驻服务** | HTTP + 队列 + 执行器池 | 多租户、多员工、要弹性 | 复杂度最高，运维成本跟着涨 |

**选择判据只有一条**：员工包里会不会出现"别人的代码"（客户自建、第三方包、外部 MCP 连接）。会，就必须走到独立进程或更强隔离；不会，进程内库最省事。

注意这条判据说的是"隔离级别"，不是"必须常驻"。**常驻是部署选择，隔离是架构选择**，两者别混：你完全可以让一个常驻服务按需拉起短命子进程去执行每个任务。

### 2.3 最小运行体长什么样

听着玄，落到代码上很小：

```ts
interface Runtime {
  // 装载：读定义、校验、注册能力。失败要说清是哪一条不合格。
  open(def: EmployeeDef, instance: EmployeeInstance): Promise<Runtime>;

  // 接活：只落库、返回任务号，不等执行。接口是"提交"而不是"执行"。
  submit(input: TaskInput): Promise<TaskId>;

  // 执行：从状态层恢复 → 干活 → 提交。这是唯一会跑模型的地方。
  run(taskId: TaskId, lease: Lease): Promise<void>;

  // 观察：状态、事件、产物，都是可查询的。
  inspect(taskId: TaskId): Promise<TaskView>;

  // 取消：给出原因，并把在途的动作收尾干净。
  cancel(taskId: TaskId, cause: Cause): Promise<void>;
}
```

五个方法对应五件事：装载、提交、执行、观察、取消。其中 `submit` 与 `run` 分开是最容易被忽略、也最值钱的一条——**提交只是写一行记录，执行是另一件事**。混在一起的后果就是"点一下按钮，界面转圈十分钟，转完什么都没留下"。

**做错的样子**：运行体里出现了"我们公司某某业务"的分支；或者它同时管着装包、解压、跑迁移。

**一行验收**：把运行体进程 `kill -9`，重启后这次任务是"被正确接管"还是"永远停在 running"？（这条其实是在验收决定六。）

## 3. 决定三：它凭什么知道该干什么

同一个员工，第一次派的活和第一百次派的活，凭什么给出风格一致、口径一致的答案？靠的是**上下文装配**：在把请求发给模型之前，把"它该知道的"拼进去。

装配的是五样东西，各有各的注入时机和预算：

| 组成 | 内容 | 什么时候进上下文 | 超预算怎么办 |
| --- | --- | --- | --- |
| **岗位说明** | 职责、边界、交付格式、口径 | 每次必进，稳定前缀 | 不裁，它必须是常量 |
| **长期记忆** | 用户偏好、历史结论、已定规则 | 按相关度检索，分级注入 | 按分数截断，宁少勿多 |
| **知识** | 文档、FAQ、规程 | 按需检索（工具化） | 检索不到就不给，别硬塞 |
| **工具清单** | 能调什么、参数是什么 | 按需声明（见决定四） | 只留本次相关，其余隐藏 |
| **历史** | 本次任务已发生的对话与工具结果 | 逐轮累加 | 压缩、裁剪大结果 |

### 3.1 记忆分三层，而且要会忘

"记忆"这个词被用得太宽，实际至少是三层，混在一起就会出问题：

| 层 | 内容 | 存在哪 | 怎么用 |
| --- | --- | --- | --- |
| **会话记忆** | 这次任务里说过的话、调过的工具 | 本次执行的状态 | 逐轮进上下文，超长就压缩 |
| **长期记忆** | 用户偏好、历史结论、已定口径 | 数据库，按 scope 隔离 | 按相关度检索，分级注入 |
| **知识** | 文档、规程、FAQ | 文档库 / 向量库 | 工具式检索，按需取 |

三条规则比分层本身更重要：

**一、记忆要有 scope。** 至少区分"这个人的"、"这个群的"、"这个租户的"。scope 错了，A 客户的偏好会漏到 B 客户那里，这是事故不是 bug。

**二、写记忆要有门槛。** 不是每轮对话都写。通常只在三种时机写：任务结束时的结论、用户明确表达的偏好、人工纠正过的错误。其余的交由"候选"机制，攒到一定量再让人确认。

**三、记忆要会忘。** 有失效时间、有冲突处理（新结论覆盖旧结论时要标记旧条失效，而不是简单追加）、有删除入口（用户说"忘了这件事"要真的能删掉）。只增不减的记忆，半年后就是一堆互相矛盾的断言。

**做错的样子**：把所有对话历史当作记忆全量塞进上下文；或者记忆只增不删，最后模型在一堆旧结论里挑一个执行。

**一行验收**：能不能回答"它为什么会记得这件事"——记得是哪次任务写进去的、依据是什么？

### 3.2 三条经验，比任何抽象原则都好使


**一、岗位说明是"岗位说明书"，不是"人格设定"。** 它该写清楚：你负责什么、不负责什么、交付物长什么样、遇到边界情况问谁。写"你是一位专业、耐心、有温度的助手"不产生任何约束力。

**二、上下文必须可复现。** 同样的任务、同样的定义版本，应该装配出同样的上下文。做不到这点，出问题时你无法回答"它当时看到了什么"，只能猜。

**三、给上下文装预算。** 不是"能塞多少塞多少"，而是给每一类分配额度，超了就按策略裁：记忆按分数截断、知识不检索就不给、工具结果超长只留摘要和引用、历史太长就压缩。

**做错的样子**：把所有历史一股脑塞进去（第 30 轮之后开始胡说）；把二十个工具全部声明（模型选错工具的概率随数量上升）；在岗位说明里写满业务规则（规则一改就要发版，而它本该是配置）。

**一行验收**：同一个任务重放两次，装配出的上下文是否一致？不一致，先修这里，别急着调模型。

## 4. 决定四：它能碰什么

这是安全与能力的分界线，也是最容易"裸奔"的地方。核心原则一句话：**模型决定"要做什么"，但决定不了"能碰什么"。**

落地就是三道闸，顺序不能变：

1. **参数校验**：模型给的工具名、参数先按 schema 校验，不过就回填错误让它重来（不要抛异常中断，模型往往第二次就对了）。
2. **权限与审批**：按员工策略判"这个动作它有没有资格做"；高危动作（转账、删除、对外发送）走审批，审批人看到的是"将要发生什么"而不是"它想干什么"。
3. **短时凭据**：真正执行的那一刻才下发凭据，限定范围、限定时间、可追溯。凭据不进上下文，也不进提示词。

配套的是**给动作分类**，这决定崩溃恢复时能不能重放：

| 类别 | 例子 | 恢复时怎么处理 |
| --- | --- | --- |
| `read` | 查订单、读文档、搜索 | 可以安全重放 |
| `write` | 建工单、发消息 | 带幂等键才可重放，否则标"可能已执行" |
| `gated` | 退款、删除、对外承诺 | 绝不自动重放，转人工确认 |

**审计要能回答四个问题**，回答不了就等于没审计：

- 谁发起的（人 / 触发器 / 另一个员工）？
- 用什么身份执行的（哪把凭据、哪个租户）？
- 碰了哪些数据（读还是写、改了哪几行）？
- 崩了会怎样（能不能重放、重放会不会重复）？

**做错的样子**：一把管理员 token 塞进环境变量，所有工具共用；工具实现里藏业务判断；审计只记"调用了 search_order"，不记参数和结果。

**一行验收**：随便挑一次工具调用，能不能当场答出上面四个问题？

## 5. 决定五：谁叫醒它

前面四个决定都在回答"它醒来之后怎么干"，这一条回答"它什么时候醒"。很多人把它当成小事——"加个定时器不就完了"——但它是架构里最容易被低估的一环。

四类触发，处理方式完全不同：

| 触发 | 例子 | 关键问题 |
| --- | --- | --- |
| **人** | 群里 @ 它、界面上提交 | 入口要能接结构化输入，不只是聊天 |
| **定时** | 每天早上 9 点出日报 | 多副本会不会重复跑；错过一次补不补 |
| **事件** | 工单创建、订单状态变更 | 事件可能重复投递、可能乱序 |
| **Webhook** | 外部系统回调 | 要能验签、要能去重、要能快速返回 |

不管哪一类，都要落成同一种东西：**一条"该干这件事"的记录（occurrence）**，而不是直接开始干活。这条记录至少要带四个要素：

```
(automationId, triggerId, triggerRevision, triggerEventKey)
```

四个字段组成唯一键——**重复触发只会冲突，不会重复执行**。这是整篇文章里投入产出比最高的一行设计。

然后补三条策略，缺一条都会在生产上咬人：

- **错过怎么办**：允许"跳过"、"只补最近一次"、"全部补"。默认应该是"只补最近一次"，全补会在服务重启后排山倒海。
- **撞车怎么办**：同一个员工同时来了五个任务，是排队、跳过、还是顶掉旧的。默认排队，但队列要有上限。
- **配置改了怎么办**：occurrence 落库时**冻结当时的配置快照**。否则今天改了日报模板，昨天正在跑的那次也会跟着变。

**做错的样子**：起一个常驻进程 `while(true) { sleep(60); if (now === 9am) run(); }`——进程挂了任务静默消失，开两个副本客户每天收到两条日报，改一次配置影响所有历史任务。

**一行验收**：把执行器开两个副本，同一时刻的任务会不会被执行两次？

## 6. 决定六：崩了丢不丢活

前五条决定"能不能干成"，这一条决定"崩一次会不会白干"。数字员工和脚本的根本差别就在这里。

### 6.1 两条铁律

**先落库，再干活。** 任务记录必须在模型第一次被调用之前写下去。反过来（先调模型，成功了再记）在崩溃时会丢掉一切痕迹。

**先提交，再展示。** 产物写进状态层之后才通知人。反过来会出现"人已经看到结果，系统里却没有这条记录"——这类 bug 极难查，因为看日志一切正常。

### 6.2 意图与执行要分开

工具调用不能一步做完"决定调 + 真去调"，中间要落一次**意图**：

```
{ phase: "execute", tool: "refund", args: {...}, replay: "unsafe" }
```

崩溃后恢复时，看到这条意图就知道"有个动作可能已经发出去了"，而不是完全不知道干到哪。这个设计在 Pi 里叫 `replay` 标记（`safe` / `unsafe`），在 DSH 里体现为"为被跳过的工具调用补一条合成失败结果"——两家做法不同，动机一致：**让重放的结果是可预期的**。

  B -->|不在| C["丢弃：这次从未开始"]
  B -->|在| D{"最后一个 checkpoint 是哪一步？"}
  D --> E{"这一步有副作用吗？"}
  E -->|read| F["安全重放"]
  E -->|write + 幂等键| G["带幂等键重放"]
  E -->|gated / 无幂等键| H["标记为『可能已执行』<br/>转人工确认"]
  F --> I["继续执行"]
  G --> I
  H --> J["结束并通知，不自动继续"]
  I --> K{"重复崩溃超过上限？"}
  K -->|是| L["标记 failed，交给人"]
  K -->|否| I
{% endmermaid %}

要点四个：

1. **在飞的请求不重发。** 崩溃时正在等模型响应的那次请求，恢复后应该记为"失败的一次尝试"并退避重试，而不是原样重发——否则你会为一个可能已经生效的调用付两次钱。
2. **重试次数按任务累积，不按进程累积。** 否则每次重启清零，一个坏任务可以无限重试。
3. **要有一个重启上限。** 连续崩溃 N 次（N 通常 3~5）就收手，标记失败并通知人。
4. **收尾要一致。** 被跳过的工具调用必须补一条"已中止"的结果写进历史，否则下一次重放时模型看到的对话是残缺的，行为不可复现。

### 6.4 租约，别让两个执行器抢同一个任务

领活时写"我持有这个任务到某时刻"，执行中定期续约，过期就允许别人接管。没有租约，重启后的旧进程和新进程可能同时干同一件事。

**做错的样子**：进程一重启，任务永远停在 `running`；或者超时重试导致客户收到两张券。

**一行验收**：在工具执行到一半时 `kill -9`，重启后看任务是"被接管并继续"还是"永久卡死"。

## 7. 决定七：你怎么知道它干得对

这一条最容易被推到"以后再说"，然后它就成了这个项目唯一的黑盒。判断标准很朴素：**随便挑一天，你能不能重建它那一整天干了什么。**

需要的是**事件流**，不是日志。日志是给人读的文本，事件是可以查询、可以重放的结构化记录：

| 事件 | 什么时候写 | 用来回答 |
| --- | --- | --- |
| `task/created` | 提交时 | 谁派的、什么时候、输入是什么 |
| `run/started` | 领活时 | 哪个执行器、用哪个版本的定义 |
| `context/assembled` | 装配后 | 这次它看到了什么（记忆/知识/工具清单快照） |
| `tool/called` | 工具执行前后 | 调了什么、参数、结果、耗时、身份 |
| `run/finished` | 提交时 | 产出什么、为什么结束 |
| `memory/written` | 沉淀记忆时 | 记住了什么、依据是什么 |

把事件流接上三个用途，才算闭环：

- **查账**：某一天花了多少 token、调了多少次外部接口、改了多少条数据。
- **回放**：拿同一个任务同一份上下文重跑，看结论是否稳定（这也是评测的基础）。
- **评测**：固定一批任务做回归，改一次岗位说明就跑一遍，看是变好还是变坏。

再加一层**预算**：token、墙钟时间、外部调用次数、费用，四个维度都要能设上限，并且能按员工/任务继承与扣减。散落在各处的 `timeout` 不是预算，它只能防止单个调用挂死，防不住"一个任务跑了两小时烧掉两百块"。

**做错的样子**：出问题只能翻应用日志，翻完还是不知道"它当时为什么这么答"。

**一行验收**：随机抽一个已完成的任务，能不能在五分钟内重建它的完整时间线？

## 8. 决定八：怎么装第二个、第一百个

第一个员工可以手工装，第一百个不行。这一条是我最初漏掉的，也是"架构"和"能跑起来"的分水岭。

需要回答四个问题：

**一、包从哪来、谁装。** 员工定义应该是一个**可安装的包**（npm、私有 registry、Git 仓库都行），而不是"复制一个目录"。装的动作由部署工具做，不由运行体做。

**二、版本怎么钉。** 每个员工的实例记录上要写死"我跑的是哪个版本"。这样两个员工可以分别停留在 v3 和 v7，升级是**逐个实例**的动作，而不是全局动作。反过来，如果所有员工共用一份全局安装目录，两个员工要不同版本时只能打架。

**三、隔离到什么程度。** 这应该是**员工属性**，不是全局设置：

| 级别 | 适用 | 隔离手段 |
| --- | --- | --- |
| `trusted` | 自己写的包 | 同进程，靠代码评审 |
| `standard` | 内部第三方的包 | 独立进程 + 降权 + 只读挂载 |
| `untrusted` | 客户自制 / 外部 MCP | 容器或 microVM + 网络出口管控 |

{% mermaid %}
flowchart LR
  P["员工包是谁写的？"] -->|自己团队| A["trusted<br/>同进程 + 代码评审"]
  P -->|公司内其他团队| B["standard<br/>独立进程 + 降权 + 只读挂载"]
  P -->|客户自制 / 外部 MCP| C["untrusted<br/>容器或 microVM + 出口管控"]
  A --> A2["成本最低<br/>风险由评审兜住"]
  B --> B2["隔离故障与权限<br/>启动开销可接受"]
  C --> C2["默认不可信<br/>网络与文件都要收口"]
{% endmermaid %}

**四、多租户怎么分。** 记忆要按 scope 隔离（个人的、群组的、租户的），凭据要按引用隔离（实例里存的是"引用哪个凭据"，不是凭据本身），配额要按租户计量。

**做错的样子**：宿主兼任安装器（解压、装依赖、跑迁移），装一个坏包把所有人带走；或者所有员工共用一个全局 `node_modules`，版本永远对不齐。

**一行验收**：两个员工要用不同版本的工具包，能不能同时存在并各自正常工作？

## 9. 把八个决定串起来：一次派活的全过程

概念讲完了，看一次真实流动。场景很普通：业务方在群里 @ 售后专员，「帮我看看这个客户为什么退单」。

{% mermaid %}
sequenceDiagram
  participant U as 业务方
  participant T as 触发层
  participant I as 实例记录
  participant R as 运行体
  participant M as 模型
  participant X as 外部系统
  U->>T: @ 一条消息
  T->>I: 生成 occurrence（四元唯一键去重）
  I->>R: 按实例钉住的版本装载定义
  R->>R: 装配上下文（岗位 + 记忆 + 知识 + 工具清单）
  R->>M: 请求（带能力清单快照）
  M-->>R: 调 search_order(orderId)
  R->>R: 校验参数 → 判权限 → 换短时凭据
  R->>X: 执行（带幂等键）
  X-->>R: 结果（大结果只留引用）
  R->>M: 回填结果
  M-->>R: 结论 + 交付格式
  R->>I: 一个事务提交：产物 + 记忆 + 事件
  I-->>U: 通知（提交之后才发）
{% endmermaid %}

把这条链路拆开，每一步都落在某个决定上：

| 步骤 | 落在哪个决定 | 这一步失败会怎样 |
| --- | --- | --- |
| occurrence 去重 | 5 触发 | 同一条消息跑两遍，客户收到两份结论 |
| 按实例的版本装载 | 1 形状 + 8 交付 | 灰度升级时一半任务用了新版本、一半用旧版本，结论对不上 |
| 装配上下文 | 3 装配 | 它看到的背景和上次不一样，行为飘 |
| 参数校验 + 判权限 + 换凭据 | 4 能力 | 越权操作，或者凭据泄漏 |
| 执行带幂等键 | 6 恢复 | 重试导致重复动作 |
| 一个事务提交 | 6 恢复 | 产物写了、记忆没写，下次它不记得这次结论 |
| 提交之后才通知 | 6 恢复 | 人看到结果，系统里没有这条记录 |

三个看起来"多余"其实救命的动作，都在这张表里：

1. **派活时只写记录、不立刻执行**——所以接口能在毫秒内返回，任务不会因为模型慢而超时。
2. **调工具前先落一次意图**——所以崩溃后知道"有个动作可能发出去了"。
3. **通知放在提交之后**——所以"人看到的"永远等于"系统里有的"。

## 10. 八个决定，一张表

| # | 决定 | 默认答案 | 做错的症状 | 一行验收 |
| --- | --- | --- | --- | --- |
| 1 | 它是什么形状的资产 | 定义（包）+ 实例（记录）+ 运行（短命执行） | 改提示词要发版；复制员工要复制代码 | 新增员工需要改代码吗 |
| 2 | 谁来跑它 | 运行体只做装载/提交/执行/观察/取消 | 运行体里长出业务分支、装包逻辑 | `kill -9` 后任务能否被接管 |
| 3 | 它凭什么知道该干什么 | 五件东西分级装配 + 上下文预算 | 全量塞历史、全量声明工具 | 同任务重放，上下文是否一致 |
| 4 | 它能碰什么 | 校验 → 权限/审批 → 短时凭据；动作分类 | 一把万能 token；审计只有"调了什么" | 能否答出审计四问 |
| 5 | 谁叫醒它 | 触发落成 occurrence 记录 + 四元唯一键 | 常驻 sleep 循环；多副本双跑 | 两个副本会不会跑两遍 |
| 6 | 崩了丢不丢活 | 先落库再干活；意图先落库；按分类重放 | 任务永久卡 running；重试导致重复副作用 | 执行到一半 `kill -9` |
| 7 | 你怎么知道它干得对 | 结构化事件流 + 四维预算 + 回放评测 | 只有文本日志，查不动 | 五分钟内能否重建时间线 |
| 8 | 怎么装第一百个 | 包 + 实例级版本 + 隔离级别作为员工属性 | 宿主兼任安装器；全局单版本 | 两个员工能否用不同版本 |

这张表有个用法：**当成评审清单**。设计评审时逐行问"我们这条怎么答的"，答不上来的那一行，就是三个月后你会踩的坑。

如果只能记住一句，记这一句：**前四条决定"能不能干成"，后四条决定"敢不敢上线"。**

## 11. 落到具体引擎：两条路线怎么填这张表

上面的八条与框架无关。真到动手时，你总要选一个底座。目前两个开源选择的路子差别挺大，用同一张表对照一下：

| 决定 | Pi 的答案 | DSH 的答案 |
| --- | --- | --- |
| **1 形状** | 员工 = npm 包，资源分 `extensions/`、`skills/`、`prompts/`、`themes/` 四类 | 员工 = 一个 profile：bundle 有序层 + `cordis.patch.yml` 补丁 |
| **2 运行体** | 一个 harness：`pi` 进程或 `pi-durable` 的服务形态 | 一个 agent loop + 工具插件，可 headless 可 web |
| **3 装配** | 系统提示现算 + 技能按需加载 + 工具延迟装载 | 分段装配（压缩、工具声明、记忆注入都有独立插件） |
| **4 能力** | 内置八个工具 + MCP（四种 exposure）+ Codemode | 工具插件 + 沙箱策略（local / seatbelt / bwrap / E2B） |
| **5 触发** | 没有内建业务定时器，交给外层调度 | 同上：loop 只管被唤醒之后，触发在外层 |
| **6 恢复** | `pi-durable`：每个 checkpoint 全量落库、`resume()`、`replay: safe/unsafe`、`requestId` 幂等 | 会话是 append-only 事件日志，重放靠事件序列 |
| **7 可观察** | transcript 条目 + `watch()` 增量流 | 会话事件流 + 压缩记录 |
| **8 交付** | `pi install npm:@x/y@1.0.0`，写进 `settings.json` | `dsh plugin --profile <p> add <pkg>`，profile 是**启动期**组合 |

两条路线各缺一块，而且缺的是同一块：

- **Pi 缺"实例"这一层。** 包和运行都齐了，但"一个具体的员工（身份 + 记忆 scope + 钉住版本 + 触发器）"要靠你在上面自己搭。`pi-durable` 给了会话与任务，但它标着 experimental，API 会变，不能当作稳定的交付层。
- **DSH 缺"运行期装配"。** profile 是启动时组合好的，适合"一套工具给所有人"；但员工是运行期概念——两百个员工要么两百个 profile/进程，要么共用一个 profile、彼此没有边界。

所以真要做产品，我的建议是把两者当**执行底座**用，自己补上中间那层：员工 = 包（定义）+ 记录（实例）+ 一次短命 Run（执行器按信任级别隔离）。**包管理器负责分发，调度器负责唤醒，durable 记录负责记忆与恢复**——三件事分别有现成的工具，不要指望一个"宿主"全包。

## 12. 什么时候别这么设计

这套东西是有成本的，规模不到就不值得。

| 场景 | 建议 |
| --- | --- |
| 一个人自用，只跑自己写的包 | 一个进程 + 一个 durable log 就够了，别拆八层 |
| 并发个位数、延迟敏感 | 同进程内跑，隔离用代码评审代替 |
| 员工定义很少变、只有一个租户 | 交付层可以先手工做，别急着做包管理 |
| 没有 durable 底座 | 先补状态层。进程隔离只解决"崩了不影响别人"，不解决"崩了这次活白干" |

最后留三条我认为不可让渡的原则，其余都可以按场景简化：

1. **员工是数据，不是进程。** 定义可版本化、实例可迁移、运行可替换。凡是把员工焊死在某个进程上的设计，都会在扩缩容那天还债。
2. **能力是员工属性，不是部署属性。** "这个员工能碰什么"写在它的定义与策略里，不写在它碰巧跑在哪台机器上。
3. **副作用必须可判定。** 每个动作都要能回答"重放会不会出事"。答不出来，就不许自动重试。
