## 0. 三个现场

第一个现场：昨天你花了二十分钟跟我确认"这个项目的日志规范是 `log.info(event, {id})`"，今天新开一个会话，我第一句话又是"你的项目用什么语言"。

第二个现场：你说过两句话——"我用 TypeScript"和"帮我查一下明天杭州的天气"。在上下文里它们是平等的两条消息，长度差不多，都会被塞进同一个窗口；但对一个助手来说，一句是长期有效的偏好，一句是一次性的查询，价值差了三个数量级。

第三个现场：一个跑了三小时的重构任务，上下文里堆着四十次工具调用的完整输出。真正决定下一步的那个结论在第八次调用里，但它已经被淹没了，模型的注意力在几千行日志上摊薄成一片。

这三个现场其实是同一个问题的三种表现：**模型本身是无状态的，而工作是有历史的。**

所谓的"Agent 记忆"，要解决的不是"把聊天记录存下来"，而是在正确的时刻，用正确的粒度，取回正确的那一小块。存是手段，取才是目的。

这半年里，四套开源实现把这件事做出了四种明显不同的答案。它们的分歧不在工程细节，而在一个更前置的问题上：**你相信"记忆"应该长成什么形状。**

## 1. 记忆系统其实只有四个动作

不管哪家，拆开看都是同一组动作：

| 动作 | 要回答的问题 | 各家的分歧点 |
| --- | --- | --- |
| 写什么 | 一段对话里，哪几句值得留下？ | 模型抽，还是显式调用 |
| 怎么组织 | 存成一条条事实，还是一棵树？ | 平铺 + 图 / 分层 / 目录 |
| 怎么取 | 下次靠什么把它捞回来？ | 向量 / 关键词 / 图 / 时间 |
| 怎么维护 | 旧的错了、过时了怎么办？ | 覆盖 / 只增 / 下钻 / 分信念 |

{% mermaid %}
flowchart LR
    A["对话流<br/>用户说、工具返回"] --> B["写入<br/>抽取 · 归并 · 去重"]
    B --> C["组织结构<br/>事实 · 分层 · 目录 · 网络"]
    C --> D["检索<br/>语义 · 关键词 · 实体 · 时间"]
    D --> E["注入上下文<br/>按预算裁剪"]
    E --> F["使用后的反馈<br/>哪条被用上了"]
    F --> B
    C --> G["维护<br/>覆盖 · 衰减 · 溯源 · 删除"]
{% endmermaid %}

四个动作里，真正拉开差距的是**第二和第四个**。

写和取是"怎么把信息搬进搬出"，只要工程做扎实，各家的效果不会差一个量级；而"怎么组织"决定了你的记忆能不能长大，"怎么维护"决定了它会不会烂掉。一个只会往里塞、不会清理和纠错的记忆系统，用三个月一定比不用更糟——它会把三周前的一个错误结论当成永久事实反复喂给模型。

下面四家，我按"它们各自把赌注押在哪个动作上"来拆。

## 2. 腾讯 TencentDB Agent Memory：把记忆做成一栋楼

第一家的直觉最朴素，也最好懂：**人对一件事的理解本来就是分层的。**

你现在能立刻说出"我同事老张不吃辣"，这是从很多次吃饭、点菜、他推掉川菜馆的具体事件里提炼出来的。你不会记得每一次点菜的菜单，但你保留了结论；需要的时候，你也能回想起"上次聚餐他换成了清汤锅"这类细节。

腾讯这套就是把这件事工程化：

| 层 | 存什么 | 用来干什么 |
| --- | --- | --- |
| L0 原始对话 | 完整对话、工具日志、原文 | 核对原话、时间戳、出处 |
| L1 原子记忆 | 从对话里抽出的事实、偏好、约束、事件 | 精确召回可执行的信息 |
| L2 场景记忆 | 按项目或场景聚合的知识块 | 快速恢复"当时在干什么" |
| L3 用户画像 | 长期稳定的画像、模式、高层认知 | 让 Agent 一步进入你的语境 |

四层之间不是并列的四个库，而是一条**提取 → 聚合 → 蒸馏**的管道：会话结束后进异步流水线，先落 L0，再抽出 L1 原子事实，同类事实聚成 L2 场景，跨场景稳定出现的模式蒸馏成 L3。

{% mermaid %}
flowchart TD
    S["会话 / 任务结束"] --> L0["L0 原始对话<br/>全量保留"]
    L0 -->|"抽取"| L1["L1 原子记忆<br/>事实 · 偏好 · 约束 · 事件"]
    L1 -->|"按场景聚合"| L2["L2 场景记忆<br/>项目上下文 · 高频路径"]
    L2 -->|"跨场景蒸馏"| L3["L3 用户画像<br/>稳定模式 · 核心结论"]
    L3 -.->|"起手就注入"| Q["下一次请求"]
    L2 -.->|"需要细节时下钻"| Q
    L1 -.->|"要原话时再下钻"| L0
{% endmermaid %}

**它最值得学的一点：检索也是分层的。**

日常请求先用 L2/L3 起手——这层信息密度最高、token 最省，相当于"先给你一份工作简报"。只有当问题需要具体事实时，才落回 L1 做 BM25 + 向量检索，再用 RRF 把两路结果融合排序；再不行，才下钻到 L0 的原话。

这个"先给结论、按需下钻"的顺序，和处理人类问题的方式一模一样。而且它天然解决了第二个现场——**不同粒度的信息不再被平等对待**：L3 的画像每次都在，L1 的碎事实只在需要时被捞。

同时，检索结果还要过三道闸：条数上限、字符预算、超时。这句话看着不起眼，但它是记忆系统能不能上生产的分水岭——没有预算的记忆，等于一个不受控的上下文注入器。

**第二件值得学的事：省 token 的不只是记忆本身。**

官方博客里提到两个配套机制：上下文卸载（把原始工具结果搬到外部文件，上下文里只留摘要和索引）和"Mermaid 无限画布"（把任务结构折叠成可导航的一张图）。这两件事严格说不属于"记忆"，但它们和记忆是同一个问题的两面：**上下文里只该放指针，不该放全文。**（我在 [DSH 会话压缩（Compaction）策略详解](https://benedicttom.github.io/2026/10/30/DSH-%E4%BC%9A%E8%AF%9D%E5%8E%8B%E7%BC%A9%E7%AD%96%E7%95%A5%E8%AF%A6%E8%A7%A3/) 里写过同一件事的另一半：压缩是"把旧的搬走"，记忆是"把有用的留住"。）

**工程形态**：这套东西不是个库，是三个服务——`memory-core`（记忆内核）、`memory-hub`（团队资产）、`proxy`（协议适配）。接入方式很有意思：**不动客户端，把 Agent 的 base URL 指向 proxy 就行**，Claude Code、Codex、OpenCode、Hermes、OpenClaw 这些都不用装插件、不用配 MCP。

数字上，官方博客给出的 OpenClaw 插件评测是：超长会话场景下 Token 最多省 **61.38%**，WideSearch 通过率从 33% 到 50%（相对 +51.52%），SWE-bench 从 58.4% 到 64.2%，AA-LCR 从 44.0% 到 47.5%；长期记忆在 PersonaMem 上把准确率从 48% 提到 76%。

**它的赌注押在哪**：组织和治理。四层是"组织结构"，Memory Hub 那一套资产登记（Chat Memory / Skill / Wiki / CodeGraph，加上 Owner、版本、可见性、ACL）是"维护结构"。这也决定了它的气质——**偏团队、偏企业、偏重**。它默认你不是一个人在用，而是一队人和一队 Agent 在共享经验。

顺带一提，它的 Wiki 层自己写明了灵感来自 Karpathy 那篇 LLM Wiki——也就是我上一篇 [LLM Wiki：不再每次去查，而是把知识编译成一座维基](https://benedicttom.github.io/2026/11/09/LLM-Wiki/) 讲的思路。这个巧合本身就说明：**"把知识编译成结构"和"把记忆分层"是同一种冲动的两个出口。**

## 3. Mem0：把记忆更新做成一条流水线

如果说腾讯的赌注是"层级"，Mem0 的赌注是**"增量"**。

它的接口只有两个动作，简单到有点简陋：`add`（存）和 `search`（取）。所有复杂性都藏在这两个动作后面。

### 3.1 写入的六个阶段

一条消息进来，`add` 背后跑的是这样一条流水线：

{% mermaid %}
sequenceDiagram
    participant A as 你的应用
    participant M as Mem0
    participant L as 抽取 LLM
    participant S as 三套存储
    A->>M: add(messages, user_id)
    M->>S: 查相关旧记忆（去重用）
    S-->>M: 候选旧事实
    M->>L: 抽取（输入 + 旧事实）
    L-->>M: 新事实（只 ADD）
    M->>M: 哈希去重 + 向量化
    M->>L: 实体链接（人 / 项目 / 组织）
    M->>L: 时间推理（何时发生、是否仍在持续）
    M->>S: 写 SQL（事实与元数据）
    M->>S: 写向量库（embedding）
    M->>S: 写实体图（关系）
{% endmermaid %}

拆开就是六步：异步入库 → 上下文查重 → 单次 LLM 抽取 → 哈希去重并向量化 → 实体链接 → 时间推理。

**这里最反直觉的一个决定是：只增不改（ADD-only）。**

用户说"我从奥斯汀搬到西雅图了"，Mem0 不会去把"用户住在奥斯汀"那条改掉，而是新增一条"用户住在西雅图"。想改？调用方显式 `update` 或 `delete`。

为什么这么设计？因为**覆盖是最容易撒谎的操作**。一旦允许"新事实覆盖旧事实"，你就丢掉了"曾经是这样"的信息，也丢掉了发现矛盾的机会。只增不改保住了完整时间线，代价是要在检索时处理冲突。

这个代价在它自己的评测里看得很清楚：LongMemEval 的 knowledge update 一类只有 **93.6**，是它所有类别里最弱的一项（单会话类已经做到 98.6）——旧事实还留着，语义相近的新旧两条会一起浮上来。

**三个存储，各管一段**：SQL 存事实与元数据（真相源、审计日志、滚动消息窗口），向量库管语义检索，实体图把"Alice"和"我同事 Alice"连起来。

### 3.2 读取的四路信号

一次 `search`，四路并行的信号：

| 信号 | 干什么 | 擅长 |
| --- | --- | --- |
| 语义 | 向量相似度 | "我怎么看远程办公"这种概念题 |
| 关键词 | BM25，做词形还原 | 人名、ID、"上周三的会" |
| 实体 | 命中记忆链上的实体加权 | "关于 Alice 我们知道什么" |
| 时间 | 写入时抽的时间元数据 vs 查询的时间意图 | "第一次提到是什么时候" |

四路打分融合成最终 top-K。注意时间这一路的设计：**它是加法项，不参与过滤**——语义相关性永远占主导，时间只是"在若干条里把日期对的那条往前挪一点"。这个细节很讲究：如果时间做成硬过滤，"上周三的会"这种问题一旦日期抽错就彻底查不到；做成加法，最坏情况也只是排位差一点。

### 3.3 数字与代价

论文（arXiv 2504.19413）的核心结论：相对 OpenAI 的记忆方案，LLM-as-a-Judge 指标上**高 26%**；带图记忆的版本比基础版再高约 2%；相比全量上下文，p95 延迟低 **91%**、token 省 **90% 以上**。

现在的文档给出的数更实：LoCoMo **92.5**（平均每次检索 6,956 token）、LongMemEval **94.4**（6,787 token）、BEAM 1M **64.1**、BEAM 10M **48.6**。

后面这组数特别值得看，因为它把"记忆到底能撑多大"摊开了：**1M token 规模还能打，10M 规模整体掉到 48.6，其中 temporal reasoning 只剩 16.3、多会话推理 26.1。**这不是 Mem0 一家的问题，是整个赛道的现状——**记忆系统在百万级上下文里还站得住，在千万级里基本失效。**

还有一个要命的细节，文档里写得很老实：上面这些分数是**平台版**的，开源 SDK 没有图记忆和平台侧的融合逻辑，开源版的实体信号只是"实体重叠加权"。**你抄的是开源版，拿到的是另一套数。**这是选型时最容易被忽略的一行小字。

**它的气质**：轻、嵌入友好、API 极简。你想在应用里加个"记住用户偏好"，`add` 一行就够；想深挖，也能换向量库、换模型、加 reranker。

## 4. OpenViking：把记忆做成一个能 `ls` 的目录

前两家都把记忆当成"数据库里的行"，火山引擎这套（字节 Viking 团队开源）反过来：**记忆就是一个文件系统。**

它在 GitHub 上的自我介绍只有一句——用文件系统组织资源、记忆和技能，供 Agent 浏览、检索、按需读取。

这个选择一旦定了，后面所有设计都跟着变。

### 4.1 四种上下文，一个 URI 空间

| 类型 | 是什么 | 谁在写 |
| --- | --- | --- |
| Resource | 原始知识与参考资料（文档、代码库、PDF） | 用户主动导入 |
| Memory | 偏好、事实、任务经验 | 从会话提取，或主动记录 |
| Skill | 一类任务的步骤、约束、脚本（`SKILL.md`） | 用户或系统 |
| Rule（Beta） | 条件下必须遵守的强约束 | 主动编译，按需召回 |

全部挂在 `viking://` 的命名空间下：`viking://resources/...`、`viking://user/{id}/memories/...`、`viking://user/{id}/skills/...`。

**在文件系统里，"记忆"和"知识"就不再是两个系统了**——它们只是同一棵树上的不同节点，用同一套 `find`/`read` 去访问。这一点比前两家都激进：它的检索不是"从记忆库里捞事实"，而是"在目录树里定位，再往下读"。

### 4.2 目录级 sidecar：L0 / L1 / L2

文件系统有个天然的毛病：Agent 不知道一个目录里有什么，只能一个个 `read`。OpenViking 的解法是给**目录**（不是文件）配两个隐藏的伴生文件：

| 层级 | 文件 | 内容 | 预算 |
| --- | --- | --- | --- |
| L0 摘要 | `.abstract.md` | 一段话说明这个目录是什么 | 256 字符 |
| L1 概览 | `.overview.md` | 更完整的目录导览 + 文件清单 | 4,000 字符 |
| L2 详情 | 原始文件 | 正文 | 不限 |

{% mermaid %}
flowchart TD
    subgraph DIR["viking://resources/docs/auth/"]
        A[".abstract.md · L0<br/>256 字符，给检索用"]
        B[".overview.md · L1<br/>4000 字符，给导航用"]
        C["oauth.md · L2"]
        D["jwt.md · L2"]
        E["api-keys.md · L2"]
    end
    A -->|"向量召回"| Q["命中的目录"]
    B -->|"rerank 与判断要不要继续读"| Q
    Q -->|"按需 read"| C
    Q --> D
    Q --> E
{% endmermaid %}

生成是自底向上的：文件先出摘要 → 叶子目录的 L1 → 叶子目录的 L0 → 聚到父目录，一层层往上冒。

这里有个工程细节我特别喜欢，因为它把"别乱刷新"写成了机制：父目录的 sidecar 带一份 `freshness` 元数据，记录直接子项总数、本轮采样了多少、还有多少变化没反映上来。直接子项超过 32 个时，用确定性采样（同一棵树重复刷新选到同一批，减少正文抖动）；子项变化比例达到 10% 才触发父目录刷新。

**换句话说，它承认"概览一定是落后的"，并且把这个落后量化了出来**（`pending_child_changes > 0` 表示正文还读得，但已知滞后）。这种诚实在记忆系统里很少见——大多数方案假装自己的摘要永远是最新的。

### 4.3 会话提交：同步归档 + 异步提取

一次 `commit()` 分两个阶段：

- **Phase 1（请求内）**：加路径锁 → 分配归档编号 → 写 `messages.jsonl` → 更新当前消息列表 → 入持久化队列 → 返回 `task_id`
- **Phase 2（后台）**：生成结构化摘要 → 写 L0/L1 → 提取长期记忆 → 写 `memory_diff.json`（记忆变更审计）→ 写 `.done`

`memory_diff.json` 是这套设计里最有审计味的产物：本次提交新增了哪些记忆文件、改了什么（带 before/after）、删了什么（带被删内容）、哪些操作被策略跳过了（带稳定原因码）。**记忆的每一次变化都能倒查。**

内置的记忆类型也很"人"：`profile`（基本信息）、`preferences`（按主题的偏好）、`entities`（人物/项目/组织）、`events`（决策与里程碑）、`identity`（助手自己的名字与形象）、`soul`（核心原则与风格）、`cases` / `trajectories` / `experiences`（任务案例、执行轨迹、提炼出的经验）。

最后三个是联动的：开启 `experiences` 会激活完整的 Agent Evolution 流程——任务先组织成 case，执行记为 trajectory，再提炼成可复用的 experience。**这是少数把"从做过的事里学东西"写进产品的实现。**

**它的代价**：要起服务、要维护目录树的一致性、AGPL-3.0 对商业嵌入有约束；而且"可浏览"意味着人会去看、会去改，改了之后摘要可能和正文不一致（它用写保护来兜：正文可改，元数据受保护，改正文只重建该目录的向量、不重新生成语义）。

**它的气质**：透明、可读、可改。适合"我想知道我的助手到底记住了什么"的人。

## 5. Hindsight：把"事实"和"推断"分开

前三家都在回答"记忆该怎么组织"，Hindsight 问了一个更尖锐的问题：**记忆里哪些是证据，哪些是结论？**

它的论文标题就把话说全了：*Hindsight is 20/20: Building Agent Memory that Retains, Recalls, and Reflects*。它批评现有方案"模糊了证据与推断的边界"——把模型推理出来的总结和用户亲口说的事实混在一个向量库里，最后你没法解释"你凭什么这么答"。

所以它把记忆拆成**四张网**：

| 网络 | 装什么 |
| --- | --- |
| World facts（世界事实） | 客观发生过的事、说过的原话 |
| Agent experiences（Agent 经验） | Agent 自己做过什么、结果如何 |
| Entity summaries（实体摘要） | 关于某个人/项目的综合认识 |
| Evolving beliefs（演进中的信念） | 会随时间修正的判断 |

{% mermaid %}
flowchart LR
    C["对话流"] --> X["抽取<br/>结构化事实 + 实体消解 + 时间索引"]
    X --> N1["世界事实"]
    X --> N2["Agent 经验"]
    N1 --> N3["实体摘要<br/>由事实合成"]
    N2 --> N4["演进中的信念<br/>会随新证据修正"]
    N3 --> R["recall<br/>四路检索 + 重排"]
    N4 --> R
    N1 --> R
    N2 --> R
    R --> RF["reflect<br/>跨记忆推理"]
    RF --> M["mental models<br/>会自动更新的活文档"]
    M -.-> R
{% endmermaid %}

四张网之上是三个操作：`retain`（存）、`recall`（取）、`reflect`（想）。

- `retain` 不做"存原文"，而是抽事实、做实体消解（"Alice" 和 "工程部的 Alice" 是同一个人）、打时间索引、生成向量；
- `recall` 四路并行——语义、BM25、实体图遍历、时间过滤——**再用 cross-encoder 重排**。重排这一步是它和前几家的关键差异：向量召回只保证"大致相关"，交叉编码器才保证"真的相关"；
- `reflect` 拿记忆去推理，回答"基于你知道的，建议我用什么技术栈"这类需要连点成线的问题。

`mental models` 是我觉得最实用的设计：**会自动更新的活文档**。你说"建一个叫『我的技术栈』的模型，跟踪我用哪些语言和框架"，之后每来一条新记忆它就在后台更新。等于把"每次都要重新 reflect 一遍"变成"预计算 + 增量维护"。

**数字很硬**：论文里，同一套 backbone 下，用 20B 的开源模型，LongMemEval / LoCoMo 整体准确率从 39%（全量上下文基线）提到 **83.6%**，并且超过全上下文的 GPT-4o；把 backbone 再放大，LongMemEval 到 **91.4%**、LoCoMo 到 **89.61%**（此前最强的开源方案是 75.78%）。

**工程形态**：一条 docker 命令起全套（API + 内嵌 PostgreSQL/pgvector + 本地 embedding + MCP 端点），任何 MCP 客户端改几行 JSON 就能接；记忆按 `bank` 隔离（`/mcp/<bank_id>/`），一个 bank 就是一颗脑子，人和项目可以各用一个。

**它的坑也写在明处**：`retain` 之后事实抽取和索引是异步的，**存完立刻查可能查不到**；`recall` 默认只回 4096 token，历史很长时会裁掉旧的低相关记忆；`reflect` 和 mental model 的生成也是异步的，第一次调用只给你一个 `operation_id`。

**它的气质**：像一个独立的记忆服务，而不是一个库。它的强项是"能解释"——事实、经验、摘要、信念分开存，答错了能定位到是哪张网、哪条证据。

## 7. 四种哲学

把表收起来，四家的分歧其实可以压缩成四句话：

**腾讯：记忆的价值在于粒度。** 同一件事，在不同抽象层上有不同的价值。L3 的一句话能省掉 L0 的五千字，而 L1 的一条事实可能是整个任务的转折点。它把"该记多细"变成了结构问题。

**Mem0：记忆的真相是时间线。** 不许覆盖——因为覆盖是一次不可逆的信息销毁。它宁愿让新旧两条并存、让检索去处理冲突，也不肯替你判断哪条是对的。

**OpenViking：记忆应该能被看见。** 如果人不能 `ls` 一下看到助手记住了什么、不能 `cat` 出来改一行，那这份记忆就不可信。它把"可解释"做成了文件系统的基本属性。

**Hindsight：记忆里必须分清证据和推断。** 用户说的话是证据，Agent 的总结是推断，两者混在一起，你就永远说不清"你凭什么这么答"。

再往下追一层：**这四种哲学其实对应四种失败模式。**

怕"记太细用不上"的，选分层；怕"覆盖掉真相"的，选增量；怕"黑箱不可控"的，选文件系统；怕"答错没法解释"的，选证据分离。

## 8. 六个坑

这六个坑不是我编的，是四家的取舍里长出来的——每一个都是某一家的强项，换到另一个场景就变成坑。

**① 把摘要当事实。** 分层和蒸馏都在生产摘要，而摘要一旦成为检索的终点、下钻链断了，它就变成了谣言。腾讯的 L2/L3 之所以强，是因为它能逐级下钻回 L0；你要是只抄了分层、没抄下钻，抄到的就是"一本没有脚注的教科书"。

**② 静默覆盖。** 反过来，覆盖看起来干净，实际是销毁证据。Mem0 的 knowledge update 分数（93.6，全场最弱）就是在提醒你：只增不改的代价是冲突共存，而这个代价是**显式**的、可观测的——比悄悄覆盖好得多。

**③ 时间丢失。** 一条没有时间戳的偏好会变成永久错误。用户三个月前说"我们还在用 MySQL"，今天已经迁到 PG 了，你的记忆库里那条还挂着"事实"的标签。Hindsight 专门开一张时间网、Mem0 专门做时间推理，都是在补这个洞。

**④ 检索预算失控。** 记忆最容易犯的错不是"没记住"，是"记住太多、每次都全塞进去"。腾讯按条数/字符/超时三重限制、Hindsight 的 recall 默认 4096 token，都是在给注入设上限。**没有预算的记忆系统，等于给上下文窗口装了一个不受控的水龙头。**

**⑤ 把"记得"当"懂了"。** `reflect` 是 LLM 在记忆上推理，产出的是新推断，不是新证据。如果不把它标成推断，下一轮它就会作为"事实"再被检索出来——这就是记忆系统里的回音室。

**⑥ 评测饱和。** LoCoMo 和 LongMemEval 已经快被打满了（单会话类 98%+），在这两个榜上刷分意义不大。Mem0 在 BEAM 10M 上掉到 48.6 才是真实水位。**看一个记忆系统，别看它在小榜上的分数，看它在千万级上下文里还剩多少。**

## 9. 怎么选

| 你的情况 | 建议 | 理由 |
| --- | --- | --- |
| 已经在用 Claude Code / Codex / DSH 这类现成 agent | 腾讯 Agent Memory | 改个 base URL 就接上，不用改客户端 |
| 在自己的应用里加"记忆"能力 | Mem0 | SDK 最轻，`add` / `search` 两个动作，存储可换 |
| 想看清助手到底记住了什么、还要能改 | OpenViking | 一切都是文件，能 `ls`、能 `cat`、能审计 |
| 只要一个记忆服务、想让记忆"会思考" | Hindsight | MCP 即插即用，事实与推断分离，能解释 |
| 企业多租户、要权限与审计 | 腾讯的团队记忆，或自己按它的四层重做 | ACL、资产、Owner 这一套它做全了 |

三句提醒：

- **别把星标当质量。** 四家都在万级星以上，但解决的是不同问题；Mem0 星最多，不代表它适合做团队知识库。
- **别只看平台版数字。** 开源版和托管版的差距，往往就藏在"图记忆""融合排序"这种一句带过的功能里。
- **先想清楚你的失败模式。** 你最怕助手犯哪种错——忘事、记错、说不清、还是太贵？答案基本就决定了选哪家。

## 10. 如果你要自己做一个

不写代码，只给五个决定，顺序不能乱：

1. **先定"记什么"。** 三类就够：事实（谁在什么时候做了什么）、偏好（长期有效的倾向）、经验（这件事该怎么干）。三类混在一起存，检索一定乱。
2. **再定"谁负责写"。** 模型自动抽（省事，但会抽歪）还是显式调用（准，但没人愿意写）？大多数生产系统是两条路都开：自动抽进候选池，显式调用直接落库。
3. **选一种组织结构。** 平铺 + 图（简单、检索强）、分层（省 token、要维护下钻链）、目录（可读、要维护一致性）——三选一，别混。
4. **检索至少两路，并且接受它不完美。** 向量管概念、关键词管精确，再加时间维度。预算一定要设：条数、字符、超时。
5. **留一条溯源链和一条删除路径。** 没有溯源的记忆是谣言；没有删除的记忆是负债——用户说"忘掉这件事"的时候，你必须真的能忘掉。

## 11. 最后

回头看那三个现场：

第一个（跨会话断裂）靠"写入 + 组织"解决；
第二个（事实与偏好混淆）靠"分层或分类"解决；
第三个（上下文膨胀）靠"检索预算 + 卸载"解决。

四家给出的答案形状不同，但它们都在回答同一个问题：**在模型无状态的前提下，什么样的外部结构，能让"经验"真的积累起来。**

我自己的判断是：这一代方案的分水岭不在存储技术，而在**你敢不敢让系统自己决定什么值得记**。四家都在不同程度上交出了这个决定权——腾讯交给分层管道，Mem0 交给抽取 LLM，OpenViking 交给目录约定，Hindsight 交给四张网。

交出去越多，省事越多，失控的风险也越大。这大概就是记忆这件事最像人的地方：**你选择记住什么，也就选择了你会变成谁。**
